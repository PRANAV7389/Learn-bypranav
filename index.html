📌 Chapter 1

What is SQL?

SQL (Structured Query Language) is the standard language for managing and querying relational databases. It lets you store, retrieve, update, and delete data.

🗄️

Database

An organized collection of structured information stored electronically — like a digital filing system.

📊

Table

Data organized in rows (records) and columns (fields) — like a spreadsheet with strict rules.

🔑

Primary Key

A unique identifier for each row. No two rows can share a primary key value.

🔗

Foreign Key

A column that references the primary key of another table — creating a relationship.

SQL Command Categories

🏗️

DDL — Data Definition

CREATE, ALTER, DROP, TRUNCATE — defines the structure of your database.

✏️

DML — Data Manipulation

INSERT, UPDATE, DELETE, SELECT — works with the data inside tables.

🔒

DCL — Data Control

GRANT, REVOKE — controls user permissions and access.

💾

TCL — Transaction Control

COMMIT, ROLLBACK, SAVEPOINT — manages transactions.

🏗️ Chapter 3

DDL — Data Definition Language

DDL commands define the structure of your database. You create tables, modify them, or remove them entirely.

CREATE TABLE

Define a new table with its columns, data types, and constraints.

SQL 
-- Create a customers table
CREATE TABLE customers (
  customer_id  INT          PRIMARY KEY AUTO_INCREMENT,
  name         VARCHAR(100) NOT NULL,
  email        VARCHAR(255) UNIQUE NOT NULL,
  city         VARCHAR(50),
  age          INT          CHECK (age >= 18),
  created_at   TIMESTAMP    DEFAULT CURRENT_TIMESTAMP
);

Common Constraints

🔑

PRIMARY KEY

Uniquely identifies each row. Cannot be NULL.

🔗

FOREIGN KEY

Links to a primary key in another table.

❌

NOT NULL

Column must always have a value.

✨

UNIQUE

No duplicate values allowed in this column.

📋

DEFAULT

Assigns a default value if none is provided.

✅

CHECK

Validates data against a boolean condition.

ALTER TABLE

Modify an existing table structure — add columns, change types, drop columns.

SQL
-- Add a new column
ALTER TABLE customers
  ADD COLUMN phone VARCHAR(20);

-- Change column data type
ALTER TABLE customers
  MODIFY COLUMN phone VARCHAR(15) NOT NULL;

-- Rename a column
ALTER TABLE customers
  RENAME COLUMN phone TO phone_number;

-- Drop a column
ALTER TABLE customers
  DROP COLUMN age;

DROP vs TRUNCATE

SQL
-- TRUNCATE: Remove all rows, keep the table structure
TRUNCATE TABLE customers;

-- DROP: Completely delete the table (structure + data)
DROP TABLE customers;

-- DROP IF EXISTS: Safe version, no error if table doesn't exist
DROP TABLE IF EXISTS customers;

DML — Data Manipulation Language

DML commands work with the actual data in your tables. INSERT adds data, UPDATE modifies it, and DELETE removes it.

INSERT INTO

SQL
-- Insert a single row
INSERT INTO customers (name, email, city)
VALUES ('Alice Johnson', '[email protected]', 'Mumbai');

-- Insert multiple rows at once
INSERT INTO customers (name, email, city)
VALUES
  ('Bob Smith',   '[email protected]',   'Delhi'),
  ('Carol White', '[email protected]', 'Bangalore'),
  ('David Lee',   '[email protected]', 'Chennai');

UPDATE

Always use a WHERE clause with UPDATE! Without it, every single row gets updated.

SQL
-- Update a specific customer's city
UPDATE customers
SET city = 'Pune'
WHERE customer_id = 1;

-- Update multiple columns at once
UPDATE customers
SET 
  city  = 'Hyderabad',
  email = '[email protected]'
WHERE name = 'Alice Johnson';

DELETE

SQL
-- Delete a specific row
DELETE FROM customers
WHERE customer_id = 5;

-- Delete with multiple conditions
DELETE FROM customers
WHERE city = 'Delhi'
  AND created_at < '2023-01-01';

SQL

🎯 Chapter 6

WHERE & Filtering

The WHERE clause filters rows based on conditions. It's one of the most powerful tools for querying specific data.

Comparison Operators

SQL
SELECT * FROM products WHERE price = 100;   -- Equal
SELECT * FROM products WHERE price != 100;  -- Not equal
SELECT * FROM products WHERE price > 500;   -- Greater than
SELECT * FROM products WHERE price <= 200;  -- Less or equal

Logical Operators — AND, OR, NOT

SQL
-- AND: both conditions must be true
SELECT * FROM customers
WHERE city = 'Mumbai' AND age > 25;

-- OR: at least one condition true
SELECT * FROM customers
WHERE city = 'Mumbai' OR city = 'Delhi';

-- NOT: negate a condition
SELECT * FROM customers
WHERE NOT city = 'Chennai';

Special Operators

SQL
-- IN: check if value is in a list
SELECT * FROM customers
WHERE city IN ('Mumbai', 'Delhi', 'Bangalore');

-- BETWEEN: range check (inclusive)
SELECT * FROM products
WHERE price BETWEEN 100 AND 500;

-- LIKE: pattern matching
SELECT * FROM customers
WHERE email LIKE '%@gmail.com';   -- ends with

SELECT * FROM customers
WHERE name LIKE 'A%';              -- starts with A

SELECT * FROM customers
WHERE name LIKE '_ob%';            -- _ matches exactly 1 char

-- IS NULL / IS NOT NULL
SELECT * FROM customers
WHERE phone IS NULL;

LIKE Pattern Wildcards

  • % — matches zero or more characters
  • _ — matches exactly one character
  • Example: 'A_i%' matches "Alice", "Alia", "Arid..."

INNER JOIN — Most Common

Returns only rows where there's a match in BOTH tables.

SELECT

  o.total
FROM customers c

LEFT JOIN — Keep All From Left

-- All customers, even those with NO orders
SELECT
  c.name,
  o.order_id  -- NULL if no orders
FROM customers c
LEFT JOIN orders o
  ON c.customer_id = o.customer_id;

SELECT c.name
FROM customers c
LEFT JOIN orders o
  ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;

Joining Three Tables

SQL
-- Customers + Orders + Products in one query
SELECT
  c.name         AS customer,
  p.name         AS product,
  oi.quantity,
  oi.quantity * p.price AS line_total
FROM customers     c
JOIN orders        o  ON c.customer_id  = o.customer_id
JOIN order_items   oi ON o.order_id     = oi.order_id
JOIN products      p  ON oi.product_id  = p.product_id;
📊 Chapter 8

Aggregate Functions

Aggregate functions compute a single result from a set of values. They're the backbone of analytics and reporting in SQL.

🔢

COUNT()

Count number of rows. COUNT(*) counts all rows, COUNT(col) skips NULLs.

➕

SUM()

Add up all values in a column. Ignores NULLs.

📐

AVG()

Calculate the average (mean) of a column's values.

⬇️

MIN()

Return the smallest value in a column.

⬆️

MAX()

Return the largest value in a column.

Examples

SQL
-- How many customers do we have?
SELECT COUNT(*) AS total_customers
FROM customers;

-- Total revenue from all orders
SELECT SUM(total) AS total_revenue
FROM orders;

-- Average order value
SELECT AVG(total) AS avg_order_value
FROM orders;

-- Price range of products
SELECT
  MIN(price) AS cheapest,
  MAX(price) AS most_expensive,
  AVG(price) AS average_price
FROM products;
📦 Chapter 9

GROUP BY & HAVING

GROUP BY groups rows with the same values, then applies aggregate functions to each group. HAVING filters those groups.

In a SELECT with GROUP BY, every column must either be in GROUP BY or inside an aggregate function like COUNT(), SUM(), etc.

SQL
-- Count customers per city
SELECT city, COUNT(*) AS customer_count
FROM customers
GROUP BY city
ORDER BY customer_count DESC;
Result
citycustomer_count
Mumbai42
Delhi38
Bangalore27
Chennai19
SQL — HAVING
-- HAVING filters groups (WHERE filters rows)
SELECT
  city,
  COUNT(*) AS count,
  AVG(o.total) AS avg_spend
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY city
HAVING COUNT(*) > 5           -- Only cities with 5+ orders
   AND AVG(o.total) > 1000      -- AND avg spend over 1000
ORDER BY avg_spend DESC;

Key Difference

  • WHERE — filters individual rows before grouping
  • HAVING — filters groups after aggregation
  • You CANNOT use aggregate functions in a WHERE clause
🪆 Chapter 10

Subqueries

A subquery is a query nested inside another query. It's a powerful way to solve multi-step problems in a single SQL statement.

Subquery in WHERE

SQL
-- Find products more expensive than the average price
SELECT name, price
FROM products
WHERE price > (
  SELECT AVG(price) FROM products
);

Subquery with IN

SQL
-- Find customers who placed orders in January 2024
SELECT name, email
FROM customers
WHERE customer_id IN (
  SELECT customer_id
  FROM orders
  WHERE order_date BETWEEN '2024-01-01' AND '2024-01-31'
);

EXISTS Subquery

SQL
-- Customers who have at least one order (EXISTS is often faster)
SELECT name
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.customer_id
);

Subquery in FROM (Derived Table)

SQL
-- Find cities where the average order is over 2000
SELECT city, avg_order
FROM (
  SELECT c.city, AVG(o.total) AS avg_order
  FROM customers c
  JOIN orders o ON c.customer_id = o.customer_id
  GROUP BY c.city
) AS city_stats
WHERE avg_order > 2000;

Indexes — The Engine of Fast Queries

An index is a separate data structure that the database maintains alongside your table to make data retrieval dramatically faster. Understanding indexes is the single most impactful skill for writing high-performance SQL.

The Problem Indexes Solve

Imagine a library with 10 million books in no particular order. To find a book about "Python", you'd have to check every single book one by one — this is what a database does without an index (called a Full Table Scan, or FTS).

Now imagine an index card catalog sorted alphabetically by topic. You flip to "P", find "Python", and the card tells you exactly which shelf and row the book is on. That card catalog is exactly what a database index is.

Without vs With Index

  • Without index: O(n) full scan — must read every row. On 10M rows: potentially 30+ seconds.
  • With B-tree index: O(log n) — binary search through the tree. On 10M rows: microseconds.
  • With hash index: O(1) — direct lookup by hash. Fastest for exact equality checks.

How B-Tree Indexes Work Internally

The most common index type is a B-Tree (Balanced Tree). Here's what happens when you create one:

The B-Tree organizes index values in a sorted tree with multiple levels:

  • Root node: Top of the tree — contains a few "pivot" values that guide navigation.
  • Branch nodes: Intermediate nodes that continue narrowing down the search.
  • Leaf nodes: Bottom level — contain the actual indexed values + a pointer (row ID) to the physical row location in the table.

When you run WHERE email = '[email protected]', the DB traverses the tree root → branch → leaf in O(log n) steps — typically 3-4 comparisons even for millions of rows. The leaf then gives a direct pointer to Alice's row.

B-Tree Traversal Example — 7 items, find 45

Root3045 > 30 → go right
Branch40 | 5040 < 45 < 50 → go between
Leaf42 | 45 | 48Found 45 → row pointer returned ✅

Types of Indexes

An index on a single column. Most basic and common type. Best for filtering by one column in WHERE, JOIN ON, or ORDER BY.

SQL — Simple Index
-- Create index on email for fast login lookups
CREATE INDEX idx_users_email
  ON users (email);

-- Now this query is O(log n) instead of O(n)
SELECT * FROM users
WHERE email = '[email protected]';

-- Create index on salary for range queries
CREATE INDEX idx_emp_salary
  ON employees (salary);

-- This range scan now uses the index
SELECT name, salary FROM employees
WHERE salary BETWEEN 50000 AND 80000;

An index on multiple columns. The order of columns matters critically — the index is most useful when your WHERE clause filters on the leftmost column(s) first. This is the leftmost prefix rule.

SQL — Composite Index
-- Index on (customer_id, order_date)
CREATE INDEX idx_orders_cust_date
  ON orders (customer_id, order_date);

-- ✅ USES the index (filters on leftmost column first)
SELECT * FROM orders
WHERE customer_id = 42;

-- ✅ USES the index (both columns)
SELECT * FROM orders
WHERE customer_id = 42
  AND order_date > '2024-01-01';

-- ❌ CANNOT use the index (skips leftmost column)
SELECT * FROM orders
WHERE order_date > '2024-01-01';
-- Reason: B-Tree is sorted by customer_id first.
-- Without filtering customer_id, entire tree must be scanned.

For an index on (A, B, C): queries filtering on A, A+B, or A+B+C use the index. Queries on B, C, or B+C alone cannot use it. Plan composite indexes around your most common query patterns.

Enforces uniqueness on a column AND creates an index. The PRIMARY KEY is always a unique index. UNIQUE constraints create unique indexes automatically. Useful for natural keys like email, phone, username.

SQL — Unique Index
-- Method 1: CREATE UNIQUE INDEX
CREATE UNIQUE INDEX idx_users_email_uniq
  ON users (email);

-- Method 2: UNIQUE constraint (same effect)
ALTER TABLE users
  ADD CONSTRAINT uq_email UNIQUE (email);

-- Composite unique index (combination must be unique)
CREATE UNIQUE INDEX idx_user_date
  ON attendance (user_id, attendance_date);
-- A user can appear many times, but not twice on the same date

-- Inserting a duplicate now throws an error
INSERT INTO users (email) VALUES ('[email protected]');
-- ERROR 1062: Duplicate entry '[email protected]' for key 'uq_email'

A covering index includes ALL columns needed by a query — so the database answers the query entirely from the index, without ever touching the base table rows. This eliminates the second "row fetch" step, making queries dramatically faster. EXPLAIN shows Using index in Extra column when a covering index is used.

SQL — Covering Index
-- Query: find customer's orders in 2024, show total
SELECT order_date, total
FROM orders
WHERE customer_id = 42
  AND order_date >= '2024-01-01';

-- Regular index: uses index to find rows, then fetches table for 'total'
CREATE INDEX idx_cust_date
  ON orders (customer_id, order_date);

-- Covering index: query answered 100% from index (no table fetch)
CREATE INDEX idx_cust_date_total
  ON orders (customer_id, order_date, total);
-- The index now contains customer_id, order_date AND total
-- → Database never needs to read actual table rows

-- EXPLAIN confirms: Extra = 'Using index' (not 'Using index condition')
EXPLAIN SELECT order_date, total
FROM orders
WHERE customer_id = 42
  AND order_date >= '2024-01-01';

A specialized index for searching natural language text inside VARCHAR or TEXT columns. Supports word-level search, relevance scoring, and Boolean operators. Much better than LIKE '%keyword%' which can't use regular indexes.

SQL — Full-Text Index
-- Create a full-text index on article title and body
CREATE FULLTEXT INDEX idx_articles_ft
  ON articles (title, body);

-- Natural language search (relevance scored)
SELECT
  title,
  MATCH(title, body) AGAINST('machine learning python') AS relevance
FROM articles
WHERE MATCH(title, body) AGAINST('machine learning python')
ORDER BY relevance DESC;

-- Boolean mode: + required, - excluded, * wildcard
SELECT title FROM articles
WHERE MATCH(title, body)
  AGAINST('+python -java machine*' IN BOOLEAN MODE);
-- Must have 'python', must NOT have 'java', optional 'machine...'

Clustered vs Non-Clustered Indexes

🗂️

Clustered Index

Determines the physical storage order of rows. Data rows ARE the leaf nodes. Only one per table (usually the Primary Key). Range scans are fast because consecutive rows are physically adjacent on disk. In MySQL InnoDB, the PK is always clustered.

📋

Non-Clustered Index

A separate structure with (indexed_value → row pointer). Many allowed per table. Requires two I/Os: one to find the pointer in the index, one to fetch the actual row. A covering index eliminates the second step.

SQL — Clustered vs Non-Clustered Behavior
-- InnoDB: PRIMARY KEY = clustered index (physical row order)
CREATE TABLE orders (
  id          INT PRIMARY KEY,       -- CLUSTERED: rows physically sorted by id
  customer_id INT,
  order_date  DATE,
  total       DECIMAL(10,2)
);

-- Non-clustered index — separate B-tree, pointer back to PK
CREATE INDEX idx_customer ON orders(customer_id);

-- Range scan on PK (clustered) → consecutive pages, very fast
SELECT * FROM orders WHERE id BETWEEN 1000 AND 2000;

-- Non-clustered lookup → finds pointer in idx_customer, then fetches row by PK
SELECT * FROM orders WHERE customer_id = 42;

Index Pitfalls — When Indexes Don't Work

These patterns silently prevent index usage and cause full table scans:

SQL — Index Anti-Patterns and Fixes
-- ❌ Wrapping an indexed column in a function → index unusable
SELECT * FROM orders WHERE YEAR(order_date) = 2024;
-- ✅ Fix: use a range instead
SELECT * FROM orders
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01';

-- ❌ Leading wildcard in LIKE → index unusable (can't seek start point)
SELECT * FROM users WHERE email LIKE '%@gmail.com';
-- ✅ Fix: trailing wildcard works fine
SELECT * FROM users WHERE email LIKE 'alice%';
-- Or use FULLTEXT index for substring searches

-- ❌ Implicit type conversion (string vs int) → index unusable
SELECT * FROM users WHERE user_id = '42';   -- user_id is INT, '42' is string
-- ✅ Fix: match the data type
SELECT * FROM users WHERE user_id = 42;

-- ❌ OR conditions across different columns → may not use index
SELECT * FROM users WHERE email = '[email protected]' OR phone = '999';
-- ✅ Fix: UNION (each branch can use its own index)
SELECT * FROM users WHERE email = '[email protected]'
UNION
SELECT * FROM users WHERE phone = '999';

-- ❌ NOT IN / NOT LIKE on non-indexed column → full scan
-- ❌ NULL comparison (IS NULL on non-indexed column) → full scan
-- ✅ Fix: ensure the column has an index and avoid negations where possible

Views & Materialized Views

A view is a named, saved SQL query that behaves like a virtual table. A materialized view goes further — it physically stores the query result for instant retrieval. Together they are essential tools for organizing complex SQL and supercharging dashboard performance.

Regular Views — Virtual Tables

A view stores only the SQL query definition, not the data. Every time you query a view, the underlying query runs fresh. Think of it as a macro or alias for a complex query.

  • Security: Expose only specific columns — hide salary, PII, passwords from certain users.
  • Abstraction: Application code queries vw_active_orders instead of a 10-table JOIN — schema changes only need to be updated in the view.
  • Reusability: Write a complex JOIN once, reference it everywhere without copy-pasting.
  • Simplicity: Give business-friendly names to technical queries.

Creating and Using Views

SQL — View Lifecycle
-- CREATE VIEW: save a complex query as a named view
CREATE VIEW vw_premium_customers AS
  SELECT
    c.id,
    c.name,
    c.email,
    COUNT(o.id)        AS order_count,
    SUM(o.total)       AS lifetime_value,
    MAX(o.order_date)  AS last_order
  FROM customers c
  JOIN orders o ON c.id = o.customer_id
  GROUP BY c.id, c.name, c.email
  HAVING SUM(o.total) > 10000;

-- USE VIEW: query it exactly like a table
SELECT * FROM vw_premium_customers
WHERE order_count > 5
ORDER BY lifetime_value DESC;

  vpc.name,
  vpc.lifetime_value,

FROM vw_premium_customers vpc

CREATE OR REPLACE VIEW vw_premium_customers AS
  SELECT
    c.id, c.name, c.email,
    SUM(o.total) AS lifetime_value
  FROM customers c

Materialized Views — Stored Snapshots

A materialized view (MV) is like a regular view, except it physically stores the query result on disk. It behaves like a cached table. Querying it is instant — no complex JOINs or aggregations run at query time. The trade-off: the data must be periodically refreshed to stay up to date.

⚡

Read Performance

Query a complex 8-table JOIN with aggregations in milliseconds instead of seconds. Pre-computed results sit ready on disk.

📊

Dashboard Power

Perfect for executive dashboards, KPI cards, and reports that millions of users view — compute once, serve to all.

🔄

Controlled Staleness

Data is stale between refreshes (minutes to hours). Acceptable for analytics; not for real-time transactional data.

Materialized View in PostgreSQL (Native Support)

SQL — PostgreSQL Materialized View
-- CREATE MATERIALIZED VIEW: computed and stored on disk NOW
CREATE MATERIALIZED VIEW mv_monthly_sales_summary AS
  SELECT
    DATE_TRUNC('month', o.order_date)    AS month,
    c.country,
    p.category,
    COUNT(DISTINCT o.id)                  AS order_count,
    COUNT(DISTINCT o.customer_id)          AS unique_customers,
    SUM(oi.quantity)                       AS units_sold,
    SUM(oi.unit_price * oi.quantity)       AS gross_revenue,
    AVG(o.total)                            AS avg_order_value
  FROM orders       o
  JOIN customers    c  ON o.customer_id  = c.id
  JOIN order_items  oi ON o.id           = oi.order_id
  JOIN products     p  ON oi.product_id = p.id
  GROUP BY 1, 2, 3
WITH DATA;
-- WITH DATA: compute and store immediately
-- WITH NO DATA: create shell, populate later on first REFRESH

-- QUERY IT: fast as a simple table scan (no joins at runtime)
SELECT month, SUM(gross_revenue) AS total_rev
FROM mv_monthly_sales_summary
WHERE country = 'India'
GROUP BY month
ORDER BY month;

-- REFRESH: update the stored data
REFRESH MATERIALIZED VIEW mv_monthly_sales_summary;

-- REFRESH CONCURRENTLY: allows reads while refreshing (needs unique index)
CREATE UNIQUE INDEX ON mv_monthly_sales_summary (month, country, category);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_monthly_sales_summary;

-- INDEX on materialized view (just like a regular table)
CREATE INDEX ON mv_monthly_sales_summary (month);
CREATE INDEX ON mv_monthly_sales_summary (country);

-- DROP
DROP MATERIALIZED VIEW mv_monthly_sales_summary;

Simulating Materialized Views in MySQL

MySQL does not natively support materialized views. The standard approach is to use a summary table and populate it via a scheduled job or stored procedure:

SQL — MySQL Materialized View Pattern
-- Step 1: Create the summary table (this IS your materialized view)
CREATE TABLE mv_daily_revenue (
  report_date   DATE           NOT NULL,
  country       VARCHAR(50),
  category      VARCHAR(50),
  order_count   INT            DEFAULT 0,
  gross_revenue DECIMAL(15,2) DEFAULT 0,
  refreshed_at  DATETIME       DEFAULT NOW(),
  PRIMARY KEY (report_date, country, category)
);

-- Step 2: Stored procedure to refresh data
DELIMITER $$
CREATE PROCEDURE RefreshDailyRevenue()
BEGIN
  -- Clear yesterday's data and recompute
  DELETE FROM mv_daily_revenue
  WHERE report_date = DATE_SUB(CURDATE(), INTERVAL 1 DAY);

  INSERT INTO mv_daily_revenue
    (report_date, country, category, order_count, gross_revenue)
  SELECT
    DATE(o.created_at)         AS report_date,
    c.country,
    p.category,
    COUNT(DISTINCT o.id),
    SUM(oi.unit_price * oi.quantity)
  FROM orders       o
  JOIN customers    c  ON o.customer_id  = c.id
  JOIN order_items  oi ON o.id           = oi.order_id
  JOIN products     p  ON oi.product_id = p.id
  WHERE DATE(o.created_at) = DATE_SUB(CURDATE(), INTERVAL 1 DAY)
  GROUP BY 1, 2, 3;
END$$
DELIMITER ;

-- Step 3: Schedule using MySQL EVENT SCHEDULER (runs daily at 2 AM)
CREATE EVENT evt_refresh_daily_revenue
ON SCHEDULE EVERY 1 DAY
STARTS TIMESTAMP(CURDATE(), '02:00:00')
DO CALL RefreshDailyRevenue();

-- Step 4: Query is now instant!
SELECT country, SUM(gross_revenue) AS revenue
FROM mv_daily_revenue
WHERE report_date = DATE_SUB(CURDATE(), INTERVAL 1 DAY)
GROUP BY country
ORDER BY revenue DESC;

Stored Procedures, Functions & Triggers

Stored procedures are named, reusable SQL programs stored inside the database itself. They encapsulate business logic, reduce network round-trips, improve security, and can contain full procedural logic — variables, loops, conditionals, and error handling.

What Is a Stored Procedure?

A stored procedure is a precompiled set of SQL statements saved under a name. Instead of sending 10 queries from your application, you send one CALL ProcedureName(). The database executes everything server-side. Benefits:

⚡

Performance

Precompiled and cached by the query optimizer. Executes faster than ad-hoc queries. Reduces network round-trips between app and DB.

🔒

Security

Grant users EXECUTE permission on a procedure without exposing the underlying tables. Prevents SQL injection via parameterization.

♻️

Reusability

Write once, call from any application — Java, Python, PHP, Power BI. Business logic lives in one place.

🧩

Modularity

Break complex operations into discrete, testable units. Procedures can call other procedures.

Procedure Parameters: IN, OUT, INOUT

Cursors — Row-by-Row Processing

A cursor lets you iterate over a result set row by row inside a procedure — useful when each row needs custom processing that can't be expressed as a set-based operation.

SQL — Cursor Example
DELIMITER $$
CREATE PROCEDURE SendRenewalAlerts()
BEGIN
  -- Variables to hold each cursor row
  DECLARE v_done       BOOLEAN DEFAULT FALSE;
  DECLARE v_cust_id    INT;
  DECLARE v_cust_name  VARCHAR(100);
  DECLARE v_expires    DATE;

  -- Declare the cursor
  DECLARE cur_expiring CURSOR FOR
    SELECT c.id, c.name, s.expires_at
    FROM customers c
    JOIN subscriptions s ON c.id = s.customer_id
    WHERE s.expires_at BETWEEN CURDATE()
      AND DATE_ADD(CURDATE(), INTERVAL 7 DAY);

  -- Handler: sets v_done = TRUE when no more rows
  DECLARE CONTINUE HANDLER FOR NOT FOUND
    SET v_done = TRUE;

  OPEN cur_expiring;

  read_loop: LOOP
    FETCH cur_expiring INTO v_cust_id, v_cust_name, v_expires;
    IF v_done THEN LEAVE read_loop; END IF;

    -- Insert an alert record for each expiring customer
    INSERT INTO alerts (customer_id, type, message, created_at)
    VALUES (
      v_cust_id,
      'renewal',
      CONCAT('Hi ', v_cust_name, ', your plan expires on ', v_expires),
      NOW()
    );
  END LOOP;

  CLOSE cur_expiring;
  SELECT ROW_COUNT() AS alerts_created;
END$$
DELIMITER ;

Cursors process one row at a time — they are significantly slower than set-based SQL for large datasets. Use them only when row-by-row processing is truly unavoidable. For most operations, a single UPDATE or INSERT...SELECT is orders of magnitude faster.

Stored Procedure — Real-World ETL Example

One of the most powerful uses of stored procedures is automating ETL (Extract, Transform, Load) pipelines entirely inside the database. Here's a production-style example that loads daily sales data into a data mart:

SQL — Daily Sales ETL Procedure
DELIMITER $$
CREATE PROCEDURE LoadDailySales(IN p_load_date DATE)
BEGIN
  DECLARE v_rows_loaded  INT DEFAULT 0;
  DECLARE v_rows_skipped INT DEFAULT 0;
  DECLARE v_error_msg    VARCHAR(500);
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    GET DIAGNOSTICS CONDITION 1
      v_error_msg = MESSAGE_TEXT;
    ROLLBACK;
    INSERT INTO etl_log (procedure_name, load_date, status, message, logged_at)
    VALUES ('LoadDailySales', p_load_date, 'FAILED', v_error_msg, NOW());
  END;

  START TRANSACTION;

  -- Delete existing data for this date (idempotent reload)
  DELETE FROM fact_daily_sales
  WHERE  sale_date = p_load_date;

  -- Load aggregated sales from staging area
  INSERT INTO fact_daily_sales
    (sale_date, customer_id, product_id, quantity, revenue, cost, profit)
  SELECT
    DATE(s.created_at)             AS sale_date,
    s.customer_id,
    si.product_id,
    SUM(si.quantity)               AS quantity,
    SUM(si.quantity * si.unit_price) AS revenue,
    SUM(si.quantity * p.cost_price)  AS cost,
    SUM(si.quantity * (si.unit_price - p.cost_price)) AS profit
  FROM stg_orders       s
  JOIN stg_order_items  si ON s.id         = si.order_id
  JOIN products         p  ON si.product_id = p.id
  WHERE DATE(s.created_at) = p_load_date
  GROUP BY 1, 2, 3;

  SET v_rows_loaded = ROW_COUNT();

  COMMIT;

  -- Log success
  INSERT INTO etl_log (procedure_name, load_date, status, rows_loaded, logged_at)
  VALUES ('LoadDailySales', p_load_date, 'SUCCESS', v_rows_loaded, NOW());

  SELECT
    p_load_date     AS loaded_date,
    v_rows_loaded   AS rows_loaded,
    'SUCCESS'       AS status;
END$$
DELIMITER ;

-- Call it for yesterday's data

CREATE PROCEDURE GetProductsPaged(

SQL — WHILE Loop (Batch Processing)
DELIMITER $$
CREATE PROCEDURE BatchDeleteOldLogs(IN p_batch_size INT)
BEGIN
  DECLARE v_deleted  INT DEFAULT 1;
  DECLARE v_total    INT DEFAULT 0;

  -- Keep deleting in batches until no rows remain
  WHILE v_deleted > 0 DO
    DELETE FROM activity_logs
    WHERE  created_at < DATE_SUB(NOW(), INTERVAL 90 DAY)
    LIMIT  p_batch_size;

    SET v_deleted = ROW_COUNT();
    SET v_total   = v_total + v_deleted;

    -- Small sleep between batches to reduce lock pressure
    DO SLEEP(0.05);
  END WHILE;

  SELECT v_total AS total_rows_deleted;
END$$
DELIMITER ;

CALL BatchDeleteOldLogs(1000);

Deleting millions of rows at once acquires a massive table lock that blocks all reads and writes. Batch deletes (1,000 rows at a time with small sleeps) reduce lock duration, keep the system responsive, and give the InnoDB undo log time to breathe.

A cursor lets you iterate through a result set one row at a time, applying logic to each. Cursors are slower than set-based operations but necessary when each row requires unique, stateful processing.

SQL — Cursor to Process Each Employee
DELIMITER $$
CREATE PROCEDURE ProcessAnnualBonuses()
BEGIN
  DECLARE v_done      INT     DEFAULT FALSE;
  DECLARE v_emp_id    INT;
  DECLARE v_salary    DECIMAL(10,2);
  DECLARE v_rating    VARCHAR(10);
  DECLARE v_bonus     DECIMAL(10,2);

  -- 1. Declare cursor
  DECLARE emp_cursor CURSOR FOR
    SELECT id, salary, performance_rating
    FROM   employees
    WHERE  is_active = TRUE;

  -- 2. Handler: set v_done=TRUE when no more rows
  DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done = TRUE;

  -- 3. Open cursor
  OPEN emp_cursor;

  -- 4. Loop through rows
  bonus_loop: LOOP
    FETCH emp_cursor INTO v_emp_id, v_salary, v_rating;
    IF v_done THEN
      LEAVE bonus_loop;
    END IF;

    -- Per-employee bonus logic
    SET v_bonus = CASE v_rating
      WHEN 'Exceeds'  THEN v_salary * 0.15
      WHEN 'Meets'    THEN v_salary * 0.08
      WHEN 'Below'    THEN 0
      ELSE                v_salary * 0.05
    END;

    INSERT INTO bonus_payments (employee_id, amount, paid_date)
    VALUES (v_emp_id, v_bonus, CURDATE());
  END LOOP;

  -- 5. Close cursor
  CLOSE emp_cursor;
  SELECT ROW_COUNT() AS bonuses_issued;
END$$
DELIMITER ;

Without error handling, a failed statement inside a procedure rolls back only that statement and continues. Using DECLARE HANDLER you can catch exceptions, roll back entire transactions, and return meaningful error messages.

SQL — Error Handling in Stored Procedures
DELIMITER $$
CREATE PROCEDURE TransferFunds(
  IN  p_from_account  INT,
  IN  p_to_account    INT,
  IN  p_amount        DECIMAL(12,2),
  OUT p_status        VARCHAR(100)
)
BEGIN
  DECLARE v_balance  DECIMAL(12,2);
  DECLARE v_error    TINYINT DEFAULT FALSE;

  -- Catch any SQL exception → set flag + roll back
  DECLARE CONTINUE HANDLER FOR SQLEXCEPTION
  BEGIN
    SET v_error = TRUE;
    ROLLBACK;
    SET p_status = 'ERROR: Transaction rolled back';
  END;

  START TRANSACTION;

    -- Check sufficient balance
    SELECT balance INTO v_balance
    FROM   accounts
    WHERE  id = p_from_account
    FOR UPDATE;  -- lock row during transaction

    IF v_balance < p_amount THEN
      SET p_status = 'ERROR: Insufficient funds';
      SET v_error  = TRUE;
      ROLLBACK;
    ELSE
      UPDATE accounts SET balance = balance - p_amount WHERE id = p_from_account;
      UPDATE accounts SET balance = balance + p_amount WHERE id = p_to_account;
      INSERT INTO transfer_log (from_id, to_id, amount, txn_time)
      VALUES (p_from_account, p_to_account, p_amount, NOW());
    END IF;

  IF NOT v_error THEN
    COMMIT;
    SET p_status = CONCAT('SUCCESS: Transferred ', p_amount);
  END IF;
END$$
DELIMITER ;

CALL TransferFunds(101, 202, 500.00, @status);
SELECT @status;

Real-World Procedure: Monthly Report Generator

This procedure ties together multiple concepts: variables, conditionals, CTEs, and multiple result sets — a pattern common in production reporting systems.

SQL — Monthly Sales Report Procedure
DELIMITER $$
CREATE PROCEDURE GenerateMonthlySalesReport(
  IN  p_year      INT,
  IN  p_month     INT,
  OUT p_total_rev DECIMAL(15,2)
)
BEGIN
  DECLARE v_start_date DATE;
  DECLARE v_end_date   DATE;
  DECLARE v_prev_rev   DECIMAL(15,2);

  -- Calculate date range
  SET v_start_date = DATE(CONCAT(p_year, '-', p_month, '-01'));
  SET v_end_date   = LAST_DAY(v_start_date);

  -- Result Set 1: Summary KPIs
  SELECT
    COUNT(DISTINCT id)          AS total_orders,
    COUNT(DISTINCT customer_id) AS unique_customers,
    SUM(total)                   AS gross_revenue,
    AVG(total)                   AS avg_order_value,
    MAX(total)                   AS largest_order
  INTO @o, @c, p_total_rev, @aov, @max
  FROM  orders
  WHERE order_date BETWEEN v_start_date AND v_end_date;

  SELECT @o AS orders, @c AS customers,
         p_total_rev AS revenue, @aov AS avg_order;

  -- Result Set 2: Top 5 products this month
  SELECT
    p.product_name,
    SUM(oi.quantity)   AS units_sold,
    SUM(oi.unit_price * oi.quantity) AS revenue
  FROM  order_items  oi
  JOIN  orders       o  ON oi.order_id   = o.id
  JOIN  products     p  ON oi.product_id = p.id
  WHERE o.order_date BETWEEN v_start_date AND v_end_date
  GROUP BY p.product_name
  ORDER BY revenue DESC
  LIMIT 5;

  -- Result Set 3: MoM growth vs last month
  SELECT COALESCE(SUM(total),0)
  INTO   v_prev_rev
  FROM   orders
  WHERE  order_date BETWEEN
         DATE_SUB(v_start_date, INTERVAL 1 MONTH)
     AND DATE_SUB(v_end_date, INTERVAL 1 MONTH);

  SELECT
    v_prev_rev                                     AS last_month_rev,
    p_total_rev                                    AS this_month_rev,
    ROUND((p_total_rev - v_prev_rev) * 100.0
           / NULLIF(v_prev_rev,0), 1)            AS mom_growth_pct;
END$$
DELIMITER ;

CALL GenerateMonthlySalesReport(2024, 11, @rev);
SELECT @rev AS nov_2024_revenue;

Triggers — Deep Dive

Triggers fire automatically in response to data changes. They are invisible to the application — no code change needed to activate them. Use them for audit logging, enforcing business rules, auto-calculating columns, and cascading changes.

SQL — Trigger Types and Examples
-- BEFORE INSERT: validate or modify data before it's saved
CREATE TRIGGER trg_before_order_insert
BEFORE INSERT ON orders
FOR EACH ROW
BEGIN
  -- Auto-set created_at if not provided
  IF NEW.created_at IS NULL THEN
    SET NEW.created_at = NOW();
  END IF;
  -- Enforce minimum order value
  IF NEW.total < 1 THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Order total must be at least 1';
  END IF;
END;

-- AFTER INSERT: update stock when an order item is added
CREATE TRIGGER trg_after_order_item_insert
AFTER INSERT ON order_items
FOR EACH ROW
BEGIN
  UPDATE products
  SET   stock_qty = stock_qty - NEW.quantity
  WHERE id        = NEW.product_id;
END;

-- AFTER UPDATE: full salary change audit log
CREATE TRIGGER trg_salary_audit
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
  IF OLD.salary <> NEW.salary THEN
    INSERT INTO salary_audit (
      employee_id, old_salary, new_salary,
      pct_change,  changed_at,  changed_by
    ) VALUES (
      NEW.id,
      OLD.salary,
      NEW.salary,
      ROUND((NEW.salary-OLD.salary)*100.0/OLD.salary,2),
      NOW(),
      USER()
    );
  END IF;
END;

-- BEFORE DELETE: soft-delete pattern (archive instead of delete)
CREATE TRIGGER trg_soft_delete_customer
BEFORE DELETE ON customers
FOR EACH ROW
BEGIN
  INSERT INTO customers_deleted
  SELECT *, NOW(), USER() FROM customers
  WHERE id = OLD.id;
END;

Slowly Changing Dimensions (SCD)

In data warehouses, dimension tables (customers, products, employees) change slowly over time — a customer moves cities, a product gets re-priced, an employee switches departments. Slowly Changing Dimensions are the patterns used to track, store, and query these historical changes.

Why SCDs Matter

📜

Historical Accuracy

When a customer order was placed, they lived in Mumbai. Even if they later moved to Delhi, reports for that order should still show Mumbai.

📊

Accurate Analytics

Sales by region should reflect the region at the time of sale — not the customer's current region. Wrong SCD handling = wrong numbers.

🔍

Audit & Compliance

Who was the account manager when a contract was signed? What was the product price at purchase time? SCDs answer these questions.

SCDs apply to dimension tables in a star/snowflake schema. The fact table stores measurements (sales, events); dimension tables provide context (who, what, where, when). When dimension attributes change, you must decide: overwrite? track history? add a new row?

SCD Type 0 — Fixed / Ignore Changes

Once a dimension attribute is written, it never changes. Any updates to the source are simply ignored. Use when data should remain fixed for historical accuracy — like a customer's original sign-up date, date of birth, or original lead source.

SCD Type 0 — Example
-- dim_customer: original_signup_source is SCD Type 0
-- Even if customer was re-acquired via a different channel, we keep the original
CREATE TABLE dim_customer (
  customer_id           INT PRIMARY KEY,
  name                  VARCHAR(100),
  original_signup_source VARCHAR(50),  -- Type 0: never updated
  signup_date           DATE          -- Type 0: never updated
);

-- ETL logic: ignore updates to Type 0 columns
UPDATE dim_customer
SET   name = 'Alice Johnson'           -- only update non-Type-0 columns
-- original_signup_source is intentionally NOT updated here
WHERE customer_id = 42;

SCD Type 1 — Overwrite (No History)

When an attribute changes, simply overwrite the old value with the new one. No history is kept. Use when the old value was an error or when historical accuracy for that attribute doesn't matter (e.g., a corrected spelling of a name, updated phone number).

When an attribute changes, insert a new row with the new values and mark the old row as expired. The table keeps the complete history. You can now query the state of a dimension at any point in time. This is the most widely used SCD type in production data warehouses.

SCD Type 4 — History Table (Mini-Dimension)

Keep a "current" dimension table for fast lookups, and a separate history table that records every change as a new row with timestamps. The main table stays lean; the history table provides the full audit trail. Useful when history is needed but the main dimension table must stay simple.

SCD Type 4 — Two-Table Pattern
-- Main table: always has current state only
CREATE TABLE dim_customer (
  customer_id  INT PRIMARY KEY,
  name         VARCHAR(100),
  city         VARCHAR(100),
  updated_at   DATETIME
);

-- History table: append-only log of every change
CREATE TABLE dim_customer_history (
  history_id   INT AUTO_INCREMENT PRIMARY KEY,
  customer_id  INT,
  name         VARCHAR(100),
  city         VARCHAR(100),
  valid_from   DATETIME,
  valid_to     DATETIME
);

-- Trigger to auto-archive before update
CREATE TRIGGER trg_archive_customer
BEFORE UPDATE ON dim_customer
FOR EACH ROW
BEGIN
  INSERT INTO dim_customer_history
    (customer_id, name, city, valid_from, valid_to)
  VALUES
    (OLD.customer_id, OLD.name, OLD.city, OLD.updated_at, NOW());
END;

-- Now update the main table — trigger auto-logs old record
UPDATE dim_customer
SET city = 'Delhi', updated_at = NOW()
WHERE customer_id = 42;

-- Query full history from history table
SELECT * FROM dim_customer_history
WHERE customer_id = 42
ORDER BY valid_from;

3

Query 2: Month-over-Month Revenue Growth

SQL — Solution
WITH monthly AS (
  SELECT
    DATE_FORMAT(o.order_date, '%Y-%m') AS month,
    SUM(oi.qty * p.price)             AS revenue
  FROM orders o
  JOIN order_items oi ON o.id = oi.order_id
  JOIN products     p  ON oi.product_id = p.id
  GROUP BY month
)
SELECT
  month,
  revenue,
  LAG(revenue) OVER (ORDER BY month) AS prev_revenue,
  ROUND(
    (revenue - LAG(revenue) OVER (ORDER BY month))
    / LAG(revenue) OVER (ORDER BY month) * 100, 2
  ) AS growth_pct
FROM monthly
ORDER BY month;

We first aggregate revenue by month in a CTE, then use LAG() to look back at the previous month's revenue and compute the % change. This is a classic analytics pattern.

SELECT
  e.name,
  d.name                                   AS department,
  e.salary,
  PERCENT_RANK() OVER (

Query: Overdue Books & Calculate Fines

SELECT

  b.title                            AS book,
  l.due_date,
  DATEDIFF(CURDATE(), l.due_date)   AS days_overdue,

    WHEN m.membership_type = 'Premium'

Query: Top Influencers by Weighted Engagement

SQL — Solution
WITH
  post_engagement AS (
    SELECT
      p.user_id,
      p.id                                              AS post_id,
      SUM(CASE WHEN i.type='like'    THEN 1
               WHEN i.type='comment' THEN 3
               WHEN i.type='share'   THEN 5
               ELSE 0 END)                               AS score
    FROM posts p
    LEFT JOIN interactions i ON p.id = i.post_id
    WHERE p.posted_at >= DATE_SUB(NOW(), INTERVAL 30 DAY)
    GROUP BY p.user_id, p.id
  ),
  user_totals AS (
    SELECT
      user_id,
      SUM(score)   AS total_score,
      COUNT(*)      AS posts_count,
      AVG(score)   AS avg_score
    FROM post_engagement
    GROUP BY user_id
  )
SELECT
  u.username,
  COUNT(f.follower_id)             AS followers,
  ut.total_score,
  ROUND(ut.avg_score, 1)           AS avg_engagement,
  DENSE_RANK() OVER (
    ORDER BY ut.total_score DESC
  )                                  AS influencer_rank
FROM users      u
JOIN user_totals ut ON u.id = ut.user_id
LEFT JOIN follows   f  ON u.id = f.following_id
GROUP BY u.id, u.username, ut.total_score, ut.avg_score
ORDER BY influencer_rank
LIMIT 20;

We use a weighted scoring system (shares worth 5x likes) inside a CASE WHEN. Two CTEs build up incrementally: first per-post scores, then per-user totals. Finally, we JOIN follower counts and use DENSE_RANK for the leaderboard.

3

Query: Cohort Retention Analysis

SQL — Advanced
-- Which month's signups are most engaged 30 days later?
WITH
  cohorts AS (
    SELECT
      id,
      DATE_FORMAT(joined_date, '%Y-%m') AS cohort_month
    FROM users
  ),
  activity AS (
    SELECT
      p.user_id,
      DATE_FORMAT(p.posted_at, '%Y-%m') AS active_month
    FROM posts p
  )
SELECT
  c.cohort_month,
  COUNT(DISTINCT c.id)                AS cohort_size,
  COUNT(DISTINCT a.user_id)           AS still_active,
  ROUND(
    COUNT(DISTINCT a.user_id) * 100.0
    / COUNT(DISTINCT c.id), 1
  )                                    AS retention_pct
FROM cohorts c
LEFT JOIN activity a
  ON c.id = a.user_id
  AND a.active_month = DATE_FORMAT(
    DATE_ADD(STR_TO_DATE(CONCAT(c.cohort_month, '-01'), '%Y-%m-%d'),
    INTERVAL 1 MONTH), '%Y-%m')
GROUP BY c.cohort_month
ORDER BY c.cohort_month;

This is a cohort retention query — a crucial metric for product analytics. We group users by the month they joined (cohort), then check if they were still active the following month. The retention % tells you product stickiness.

Database Normalization

Normalization reduces redundancy and improves data integrity by organizing tables into progressively stricter "Normal Forms." Each form builds on the last.

Why Normalize?

🔁

Eliminate Redundancy

Same data in multiple places causes update anomalies — change it once, it's stale everywhere else.

🛡️

Data Integrity

Constraints and FK relationships prevent invalid data from entering the system.

🔍

Easier Queries

Well-structured data is intuitive to query and less prone to incorrect results.

First Normal Form (1NF)

1NF: Every column must hold atomic (indivisible) values. No repeating groups or arrays in a cell.

NULL Handling

NULL represents absence of value — not zero, not empty string. It has unique behavior that trips up many developers. Master it here.

The Golden Rule

NULL ≠ NULL

Any comparison with NULL returns UNKNOWN — not TRUE or FALSE. You must use IS NULL or IS NOT NULL, never = NULL.

SQL — NULL Comparisons
-- WRONG: returns no rows
SELECT * FROM users WHERE phone = NULL;    -- ❌
-- CORRECT
SELECT * FROM users WHERE phone IS NULL;     -- ✅
SELECT * FROM users WHERE phone IS NOT NULL; -- ✅

NULL-Safe Functions

SQL — Handling NULLs
-- COALESCE: first non-NULL value
SELECT COALESCE(phone, mobile, 'No Contact') AS contact
FROM users;

-- IFNULL: two-argument shorthand
SELECT IFNULL(discount, 0) AS discount
FROM products;

-- NULLIF: returns NULL when values match (safe division)
SELECT revenue / NULLIF(units_sold, 0) AS rev_per_unit
FROM sales;

-- COUNT behavior with NULLs
SELECT
  COUNT(*)         AS all_rows,      -- includes NULLs
  COUNT(phone)    AS with_phone,   -- excludes NULL phones
  AVG(score)      AS avg_non_null  -- NULLs excluded from avg
FROM users;

-- Anti-join: customers with NO orders (LEFT JOIN + IS NULL)
SELECT c.name
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.id IS NULL;

Q&A — Beginner (30 Questions)

Core SQL fundamentals. Try to answer each question before expanding the answer.

Theoretical (Q1–Q10)

Q1. What is SQL and what is it used for? ▼

SQL (Structured Query Language) is a domain-specific language for managing relational databases. Uses: creating structures (DDL), manipulating data (DML), querying with SELECT, access control (DCL), and transaction management (TCL). Each RDBMS (MySQL, PostgreSQL, SQL Server, Oracle) has slight dialect differences on top of the ANSI/ISO standard.

Q2. What is the difference between a Database and a DBMS? ▼

A database is an organized collection of structured data. A DBMS (Database Management System) is the software that manages it — providing tools to create, read, update, delete, secure, and back up data. MySQL, PostgreSQL, Oracle, SQL Server are all DBMS software. The database is the data; the DBMS is the engine powering it.

Q3. What are the five SQL command categories? ▼
  • DDL (Data Definition Language): CREATE, ALTER, DROP, TRUNCATE — define structure
  • DML (Data Manipulation Language): INSERT, UPDATE, DELETE — manipulate rows
  • DQL (Data Query Language): SELECT — retrieve data
  • DCL (Data Control Language): GRANT, REVOKE — permissions
  • TCL (Transaction Control Language): COMMIT, ROLLBACK, SAVEPOINT — transactions
Q4. What is a Primary Key? ▼

A column (or combination) that uniquely identifies each row. Rules: must be UNIQUE, must be NOT NULL, one per table. Can be a single column (simple PK) or multiple columns (composite PK). Creates a clustered index automatically.

Q5. What is a Foreign Key? ▼

A column that references the Primary Key of another table, enforcing referential integrity. You cannot insert an FK value that doesn't exist in the referenced table. ON DELETE CASCADE/SET NULL/RESTRICT controls behavior when the referenced row is deleted.

Q6. What is the difference between DELETE, TRUNCATE, and DROP? ▼
  • DELETE: DML. Removes specific rows (WHERE clause). Can be rolled back. Fires triggers. Slow on large tables.
  • TRUNCATE: DDL. Removes ALL rows instantly. No WHERE clause. Cannot roll back in most DBs. Very fast (deallocates pages). Does not fire row-level triggers.
  • DROP: DDL. Removes the entire table structure and all data permanently.
Q7. What is the difference between CHAR and VARCHAR? ▼

CHAR(n): fixed-length, always stores n bytes (padded with spaces if shorter). Best for consistent-length values (country codes, hashes). VARCHAR(n): variable-length, stores only used bytes + 1-2 byte length prefix. Best for names, emails, descriptions. VARCHAR saves space but has a tiny overhead to read the length prefix.

Q8. What does NULL mean in SQL? ▼

NULL means absence of a value — not zero, not empty string, not false. It means "unknown" or "not applicable." Key behaviors: arithmetic with NULL = NULL; comparison with NULL = UNKNOWN; COUNT(*) includes NULLs but COUNT(col) excludes them; SUM/AVG/MIN/MAX ignore NULLs. Always use IS NULL / IS NOT NULL.

Q9. What is the difference between WHERE and HAVING? ▼

WHERE filters rows BEFORE aggregation — works on individual row values, cannot reference aggregate functions. HAVING filters groups AFTER GROUP BY — can reference COUNT(), SUM(), etc. Memory trick: WHERE = filter rows; HAVING = filter groups.

Q10. What is the logical execution order of a SELECT statement? ▼
  1. FROM / JOINs — identify source tables
  2. WHERE — filter individual rows
  3. GROUP BY — group rows
  4. HAVING — filter groups
  5. SELECT — compute output columns
  6. DISTINCT — remove duplicates
  7. ORDER BY — sort results
  8. LIMIT / OFFSET — paginate

Important: aliases defined in SELECT cannot be used in WHERE (WHERE executes before SELECT).

Q31. What are constraints in SQL? List all types. ▼

Constraints enforce data integrity rules at the database level. Types:

  • PRIMARY KEY: Unique + Not Null identifier for each row.
  • FOREIGN KEY: Enforces referential integrity between tables.
  • UNIQUE: All values in the column must be distinct (NULLs are allowed).
  • NOT NULL: The column cannot have NULL values.
  • CHECK: Values must satisfy a boolean expression (e.g., salary > 0).

Q32. What is the difference between a subquery and a JOIN? ▼

A JOIN combines rows from multiple tables into a single result set — ideal when you need columns from both tables. A subquery is a nested query that returns a value, a list, or a table used by the outer query. JOINs are generally faster because the optimizer can use indexes on both sides. Subqueries are often clearer to read and are necessary for correlated logic. For most aggregate comparisons (e.g., "above average"), a subquery is cleaner; for combining data from two tables, a JOIN is preferred.

Q33. What is a composite primary key? ▼

A composite (compound) primary key uses two or more columns together to uniquely identify a row. Neither column alone is unique, but the combination is. Common in junction/bridge tables for many-to-many relationships.

SQL

  course_id   INT,

Q34. What are aggregate functions? List them all. ▼

Aggregate functions compute a single value from a set of rows. They ignore NULLs (except COUNT(*)).

  • COUNT(*): Total row count (including NULLs)
  • COUNT(col): Count of non-NULL values
  • COUNT(DISTINCT col): Count of unique non-NULL values
  • SUM(col): Total of numeric values
  • AVG(col): Average of non-NULL numeric values
  • MIN(col): Smallest value
  • MAX(col): Largest value
  • GROUP_CONCAT(col): Concatenated string of values (MySQL)
Q35. What is the difference between a natural key and a surrogate key? ▼

A natural key is a real-world identifier that already exists in the data — like email address, PAN number, ISBN, or phone number. A surrogate key is an artificial identifier generated by the database (typically an auto-incremented integer or UUID) with no business meaning. Surrogate keys are preferred because natural keys can change (a person changes their email), can be long (degrading index performance), and may not always be available for every entity. Surrogate keys are stable, short, and fast to join on.

Q36. What is a schema? ▼

In SQL, a schema is a logical namespace that groups database objects — tables, views, indexes, stored procedures, and functions. In MySQL, "schema" and "database" are synonymous (CREATE SCHEMA = CREATE DATABASE). In PostgreSQL and SQL Server, a schema is a container within a database, allowing multiple schemas per database (e.g., sales.orders, hr.employees). Schemas help with organization, security (grant access to a schema), and avoiding name collisions.

Q37. What is ACID and why is it important? ▼
  • Atomicity: A transaction is all-or-nothing. If it fails midway, all changes are rolled back.
  • Consistency: Every transaction moves the DB from one valid state to another — all constraints remain satisfied.
  • Isolation: Concurrent transactions don't interfere. Each sees a consistent snapshot.
  • Durability: Once committed, changes survive crashes and power failures — they are written to durable storage.

ACID is critical in financial systems (bank transfers), e-commerce (order + inventory must update together), and any scenario where partial writes cause data corruption.

Q38. What is the difference between ROLLBACK and COMMIT? ▼
SQL — COMMIT vs ROLLBACK
START TRANSACTION;
  UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 1000 WHERE id = 2;

COMMIT;    -- Makes all changes permanent. Visible to other sessions.
-- or --
ROLLBACK; -- Undoes ALL changes since START TRANSACTION. DB returns to prior state.

COMMIT permanently saves the transaction. ROLLBACK cancels everything. Autocommit mode (ON by default in MySQL) automatically commits each statement unless inside an explicit transaction block.

Q39. What is a stored procedure and when would you use one? ▼

A stored procedure is a named, precompiled SQL program stored in the database. Use one when: (1) the same multi-step SQL operation runs frequently — compile once, call many times; (2) you want to restrict direct table access for security — grant EXECUTE only; (3) you need procedural logic (loops, conditionals, error handling) inside the DB; (4) you're building ETL pipelines or batch jobs that run inside the database; (5) you want to reduce network round-trips by executing multiple statements server-side in one call.

Q40. What are the different types of SQL relationships? ▼
  • One-to-One (1:1): Each row in Table A corresponds to at most one row in Table B. Example: users ↔ user_profiles. Implemented with a unique FK.
  • One-to-Many (1:N): One row in Table A corresponds to many rows in Table B. Example: customers → orders. Most common relationship. Implemented with a FK in the "many" table.
  • Many-to-Many (M:N): Many rows in A relate to many rows in B. Example: students ↔ courses. Implemented through a junction/bridge table (student_courses) with two FKs.
Q41. What is the difference between INNER JOIN and OUTER JOIN? ▼

An INNER JOIN returns only rows where there is a matching value in both tables — unmatched rows from either table are excluded. An OUTER JOIN preserves rows from one or both tables even when there's no match: LEFT OUTER keeps all rows from the left table (unmatched right rows become NULL), RIGHT OUTER keeps all from the right, and FULL OUTER keeps all from both sides.

Q42. What is SQL injection and how does parameterized queries prevent it? ▼

SQL injection is an attack where malicious SQL code is inserted into an input to manipulate queries. Example: if a login form concatenates input directly, an attacker can enter ' OR '1'='1 to bypass authentication. Parameterized queries (prepared statements) prevent this by treating user input as data, never as SQL code — the DB separates the query structure from the user-supplied values, so injected SQL syntax cannot alter the query logic.

SQL — Safe Parameterized Query
-- ❌ VULNERABLE: string concatenation
-- "SELECT * FROM users WHERE email = '" + userInput + "'"
-- Input: [email protected]' OR '1'='1 → bypasses login

-- ✅ SAFE: prepared statement (PHP PDO example)
-- $stmt = $pdo->prepare("SELECT * FROM users WHERE email = ?");
-- $stmt->execute([$userInput]);
-- Input is bound as a literal string value — cannot alter query structure

-- In stored procedures: always use parameters, never CONCAT into SQL
PREPARE safe_stmt FROM 'SELECT * FROM users WHERE email = ?';
EXECUTE safe_stmt USING @user_input;
Q43. What is a transaction? Give a real-world example. ▼

A transaction is a sequence of SQL operations treated as a single unit of work — either all succeed or all fail together. Real-world example: bank transfer. Transferring ₹1000 from account A to B requires two steps: deduct from A, add to B. If step 2 fails after step 1 succeeds, money disappears. A transaction wraps both in an atomic unit — if step 2 fails, step 1 is automatically rolled back, leaving both accounts unchanged.

Q44. What are DDL, DML, DCL, and TCL? Give one SQL command for each. ▼
  • DDL (Data Definition Language): Defines structure. Example: CREATE TABLE employees (...)
  • DML (Data Manipulation Language): Manipulates data. Example: INSERT INTO employees VALUES (...)
  • DCL (Data Control Language): Controls access. Example: GRANT SELECT ON employees TO 'analyst'@'%'
  • TCL (Transaction Control Language): Manages transactions. Example: COMMIT
Q45. What is normalization vs denormalization? ▼

Normalization organizes data into multiple related tables to eliminate redundancy and protect integrity. Better for OLTP (frequent writes, transactions). Denormalization intentionally combines data (some redundancy) to reduce JOIN complexity and improve read performance. Better for OLAP/analytics (dashboards, reports, data warehouses). The trade-off: normalized = data integrity, fewer anomalies; denormalized = faster queries, simpler analytics. Star and snowflake schemas in data warehouses are controlled forms of denormalization.

Q31. What is a constraint? Name all constraint types. ▼

A constraint is a rule enforced on table columns to ensure data validity and integrity. The main constraint types:

  • PRIMARY KEY: Uniquely identifies each row. No NULLs allowed. One per table.
  • FOREIGN KEY: References PK of another table. Enforces referential integrity.
  • UNIQUE: All values in column must be distinct. NULLs are allowed (and not counted as duplicates).

  • DEFAULT: Provides a value when none is supplied.

Q32. What is AUTO_INCREMENT? How does it work? ▼

AUTO_INCREMENT automatically generates a unique integer for a column each time a row is inserted. The DB tracks the last used value and increments it. Key facts: only one AUTO_INCREMENT column per table; it must be an integer type; must be a key (PRIMARY KEY or UNIQUE); gaps occur when rows are deleted or INSERTs are rolled back — this is normal. Use LAST_INSERT_ID() to retrieve the ID just inserted.

SQL
CREATE TABLE users (
  id   INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(100)
);
INSERT INTO users (name) VALUES ('Alice'), ('Bob');
SELECT LAST_INSERT_ID();  -- returns 2 (last auto id)

-- Reset auto_increment counter
ALTER TABLE users AUTO_INCREMENT = 1000;
Q33. What is the difference between TRUNCATE and DELETE with no WHERE? ▼

Both remove all rows from a table but work very differently. DELETE without WHERE: DML command, logs each row deletion individually (slow on large tables), can be rolled back within a transaction, fires row-level triggers, resets nothing — AUTO_INCREMENT counter stays where it was. TRUNCATE: DDL command, deallocates entire data pages (extremely fast), cannot be rolled back in MySQL (in most contexts), does NOT fire row-level triggers, and resets the AUTO_INCREMENT counter to 1.

Q34. What is a composite primary key? Give an example. ▼

A composite primary key uses two or more columns together as the unique identifier. Neither column alone is necessarily unique — but the combination must be. Commonly used in junction/bridge tables representing many-to-many relationships.

CREATE TABLE enrollments (
  student_id INT NOT NULL,
  course_id  INT NOT NULL,

Q35. What does COALESCE do? How is it different from IFNULL? ▼

COALESCE(a, b, c, ...) returns the first non-NULL value from a list of any number of arguments. It is ANSI SQL standard and works in all databases. IFNULL(a, b) is MySQL-specific and takes exactly two arguments. COALESCE is preferred because it is more portable and flexible — you can chain fallbacks. Example: COALESCE(cell, landline, email, 'Unknown') tries four columns in order.

Q37. What is the difference between IS NULL and = NULL? ▼

= NULL uses equality comparison, but NULL is not a value — it is the absence of a value. Any comparison with NULL returns UNKNOWN (not TRUE or FALSE), so WHERE phone = NULL will never return any rows. IS NULL is the correct SQL operator specifically designed to test for absence of value. Similarly, IS NOT NULL correctly finds non-NULL rows while != NULL returns zero rows.

Q40. What is the difference between a natural join and an inner join? ▼

An INNER JOIN requires you to explicitly specify the join condition with ON. A NATURAL JOIN automatically joins on all columns with the same name in both tables — no ON clause needed. NATURAL JOIN is convenient but dangerous: if you later add a column with the same name to both tables, the join condition changes silently. Best practice is to always use explicit INNER JOIN with ON for clarity and safety.

Q42. What is the LIMIT clause and how does OFFSET work with it? ▼

LIMIT n restricts the number of rows returned. OFFSET m skips the first m rows before returning results. Together they implement basic pagination. Q43. What is a CROSS JOIN? When would you actually use it? ▼

A CROSS JOIN produces the Cartesian product — every row from table A combined with every row from table B. If A has 10 rows and B has 5, the result has 50 rows. Common legitimate uses: generating all combinations for inventory (sizes × colors × materials), creating a test dataset with all date × product combinations, or building combination pricing matrices. Accidentally using CROSS JOIN on large tables is a classic performance disaster.

FROM sizes  s
CROSS JOIN colors c
ORDER BY s.size_name, c.color_name;
Q44. What is referential integrity and how do foreign keys enforce it? ▼

Referential integrity ensures that relationships between tables remain consistent — you cannot have a "child" row that references a non-existent "parent." Foreign keys enforce this in three ways: ON INSERT/UPDATE: the FK value must exist in the referenced table. ON DELETE: RESTRICT (default — block the delete), CASCADE (auto-delete child rows), SET NULL (set FK to NULL), SET DEFAULT (set FK to its default value). Example: deleting a customer with ON DELETE CASCADE automatically deletes all their orders too.

Q&A — Intermediate (35 Questions)

JOINs, subqueries, aggregates, indexes, views, stored procedures. These appear in most SQL technical interviews.

Theoretical (Q1–Q10)

Q1. Explain all types of JOINs. ▼
  • INNER JOIN: rows matching in BOTH tables. Non-matches excluded.
  • LEFT JOIN: ALL rows from left + matching right. Unmatched right = NULL.
  • RIGHT JOIN: ALL rows from right + matching left. Unmatched left = NULL.
  • FULL OUTER JOIN: All rows from both tables. Unmatched = NULL on either side. (MySQL: use LEFT UNION RIGHT.)
  • CROSS JOIN: Cartesian product — every row of A × every row of B.
  • SELF JOIN: A table joined to itself (hierarchies, comparisons within same table).
Q2. Correlated vs non-correlated subquery? ▼

A non-correlated subquery runs once independently and its result is used by the outer query. A correlated subquery references a column from the outer query, so it re-runs for each row the outer query processes. Correlated subqueries are powerful but can be slow on large tables — often replaceable with a JOIN or window function.

Q3. What is a VIEW? Advantages and limitations? ▼

A VIEW is a saved query acting as a virtual table. It stores the query definition, not the data. Advantages: simplifies complex queries, security (hide sensitive columns), reusability. Limitations: no performance benefit (query reruns each time unless materialized), some views are not updatable (those with GROUP BY, DISTINCT, aggregates, certain JOINs).

Q4. What is an index and how does it work? ▼

An index is a B-tree data structure that enables fast row lookup without a full table scan. Without index: O(n) full scan. With index: O(log n) B-tree traversal. Improves SELECT, WHERE, JOIN, ORDER BY. Slows INSERT/UPDATE/DELETE (index must be maintained). Create indexes on: WHERE columns, JOIN columns, ORDER BY columns, high-cardinality columns.

Q5. Clustered vs non-clustered index? ▼

A clustered index determines physical row order in the table (one per table — typically the PK). Data rows ARE the leaf nodes. Fast for range queries. A non-clustered index is a separate structure storing (indexed_value → row_pointer). Multiple allowed per table. Requires two lookups unless it's a covering index.

Q6. Explain 1NF, 2NF, 3NF. ▼
  • 1NF: Atomic values — no arrays or multi-values in a cell.
  • 2NF: In 1NF + no partial dependencies — every non-key column depends on the full composite PK.
  • 3NF: In 2NF + no transitive dependencies — non-key columns depend only on the PK, not on other non-key columns.
Q7. What is ACID? ▼
  • Atomicity: All operations succeed or all fail — no partial results.
  • Consistency: DB moves from one valid state to another.
  • Isolation: Concurrent transactions don't interfere.
  • Durability: Committed changes survive system failures (written to disk).
Q8. IN vs EXISTS — when to use which? ▼

IN loads all subquery results into memory. Good for small result sets. EXISTS stops at the first match (short-circuits). Better for large subquery results. Critical: NOT IN returns zero rows if the subquery returns any NULL values — use NOT EXISTS instead.

Q9. What is a self-join? Give an example. ▼

Q10. How do aggregate functions treat NULLs? ▼

COUNT(*) counts all rows including NULLs. COUNT(col) counts only non-NULL values. SUM/AVG/MIN/MAX all ignore NULLs. Important: AVG(col) ≠ SUM(col)/COUNT(*) when NULLs exist because COUNT(*) includes the NULL rows in the denominator.

Q36. What is a TRANSACTION? Explain with a real example. ▼

A transaction is a sequence of SQL operations that are treated as a single unit of work — all must succeed, or all must be rolled back. The classic example is a bank transfer: debit one account AND credit another. If the credit step fails after the debit, you'd lose money. Wrapping both in a transaction ensures atomicity.

SQL — Bank Transfer Transaction
START TRANSACTION;
  -- Debit sender
  UPDATE accounts SET balance = balance - 5000
  WHERE id = 101 AND balance >= 5000;

  -- Credit receiver
  UPDATE accounts SET balance = balance + 5000
  WHERE id = 202;

COMMIT;   -- both succeed: persist
-- ROLLBACK;  -- if anything fails: undo everything

Q39. What is query execution order and why does it matter for aliases? ▼

SQL executes logically in this order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Column aliases defined in SELECT are not available in WHERE because WHERE runs before SELECT. However, aliases ARE available in ORDER BY. This trips up many developers who write WHERE alias_name = value and get an error.

SQL

SELECT salary * 12 AS annual
FROM employees
WHERE annual > 600000;

-- ✅ WORKS: use HAVING after GROUP BY, or repeat the expression
SELECT salary * 12 AS annual
FROM employees
WHERE salary * 12 > 600000;

-- ✅ WORKS with ORDER BY (runs after SELECT)
SELECT salary * 12 AS annual
FROM employees
ORDER BY annual DESC;

Q42. What is the difference between CHAR, VARCHAR, and TEXT? ▼

Q44. What is a NATURAL JOIN and why is it risky? ▼

A NATURAL JOIN automatically joins tables on all columns with the same name — you don't specify an ON condition. Q36. What is query execution plan and how do you read it? ▼

A query execution plan (QEP) is the database engine's step-by-step strategy for executing a query. You access it via EXPLAIN (MySQL) or EXPLAIN ANALYZE (PostgreSQL). Key columns to read:

  • type: Access method — ALL (full scan, bad) → index → range → ref → eq_ref → const (optimal)
  • key: Which index is being used (NULL = no index)
  • rows: Estimated rows the engine will examine
  • Extra: "Using index" (covering index, excellent), "Using filesort" (extra sort step, add index), "Using temporary" (temp table, expensive)
Q37. What is a database transaction? Explain with a real scenario. ▼

A transaction groups multiple SQL statements into one atomic unit. Real scenario: e-commerce checkout. When a customer places an order, three things must happen together: (1) insert into orders table, (2) insert order items, (3) decrement stock. If stock update fails after the order was inserted, you'd have a ghost order. Wrapping all three in a transaction ensures either everything succeeds (COMMIT) or nothing persists (ROLLBACK). This is the Atomicity part of ACID.

Q39. What is the difference between TRUNCATE and DELETE? When to use each? ▼

Use DELETE when: you need to remove specific rows (with WHERE), need the operation logged row-by-row for recovery, need triggers to fire, or need to be able to rollback. Use TRUNCATE when: you need to clear the entire table as fast as possible, don't need row-by-row logging, don't need triggers, and auto-increment should reset to 1. TRUNCATE is 10-100x faster on large tables because it deallocates entire data pages rather than deleting rows individually.

Q40. Explain the concept of cardinality in SQL. ▼

Cardinality refers to the uniqueness of values in a column. High cardinality = many unique values (e.g., user_id, email — good candidates for indexing). Low cardinality = few unique values (e.g., boolean is_active, status with 3 values — poor index candidates). In JOINs, cardinality also describes the relationship: 1:1, 1:N, M:N. The query optimizer uses column cardinality statistics to choose the best execution plan — it prefers high-cardinality index lookups over low-cardinality full-scan patterns.

Q41. What is a covering index? How does it speed up queries? ▼

A covering index includes all columns needed by a query, so the database engine can answer the query entirely from the index without touching the base table rows. This eliminates the "row fetch" step — instead of two I/O operations (index lookup → row fetch), only one is needed. EXPLAIN shows "Using index" in the Extra column when a covering index is active. Example: if a query SELECTs order_date, total and WHERE filters on customer_id, an index on (customer_id, order_date, total) is fully covering.

Q42. What is a deadlock? How does MySQL resolve it? ▼

A deadlock is a circular wait condition where transaction A holds a lock on row 1 and waits for row 2, while transaction B holds row 2 and waits for row 1. Neither can proceed. MySQL's InnoDB engine detects deadlocks automatically by looking for wait cycles in its lock graph. When detected, it automatically selects the "cheaper" transaction to roll back (based on undo log size) and returns error 1213 to that session. The other transaction then completes. You prevent deadlocks by: accessing tables/rows in a consistent order across all transactions, keeping transactions short, and using row-level locks instead of table locks where possible.

Q44. What is partitioning? What are its types? ▼

Table partitioning divides a large table into smaller physical pieces (partitions) while maintaining a single logical view. The DB can skip entire partitions that don't satisfy a query's WHERE clause (partition pruning). Types: RANGE — partitions based on column value ranges (e.g., by year); LIST — partitions based on discrete values (e.g., by country); HASH — distributes rows evenly using a hash function (e.g., HASH(customer_id)); KEY — like HASH but uses MySQL's internal hash algorithm. Q45. What is the N+1 problem and how do you fix it? ▼

N+1 occurs when code runs 1 query to fetch N parent rows, then N separate queries for each child. Example: fetch 100 customers (1 query), then for each customer fetch their orders (100 queries) = 101 queries total. The fix is eager loading — use a JOIN to fetch parents and children in one query, or use an IN clause to batch-fetch children for all parents at once. In ORMs: use includes (Rails), select_related/prefetch_related (Django), or JOIN FETCH (JPA) to prevent lazy-loading loops.

Q46. What is a schema migration? Best practices? ▼

A schema migration is a versioned, scripted change to a database structure (adding columns, changing types, creating tables). Best practices: (1) Always add nullable columns first, backfill data in batches, then add NOT NULL constraint — never add NOT NULL without DEFAULT to a large live table (locks entire table). (2) Use migration tools (Flyway, Liquibase, Alembic) for version control. (3) Make migrations idempotent — safe to re-run. (4) Test on a production clone first. (5) For large tables (>10M rows), use online schema change tools (gh-ost, pt-online-schema-change) that swap shadow tables atomically without locking.

Q47–50. Window function theory, CTE best practices, locking types, isolation levels ▼

Q47 — Window functions: They compute a result across a "window" of rows related to the current row without collapsing those rows. PARTITION BY divides rows into groups (like GROUP BY but without collapsing). ORDER BY within OVER() defines the row order for running calculations. The ROWS/RANGE BETWEEN clause defines the window frame for aggregations like moving averages.

Q48 — CTE best practices: Name CTEs descriptively (revenue_by_month, not cte1). Use multiple CTEs in sequence for complex multi-step transformations. Avoid CTEs for single-use expressions — a subquery is simpler. In PostgreSQL, use WITH ... AS MATERIALIZED only when the CTE is referenced many times and you want to force a single execution.

Q49 — Lock types: Row-level locks (most granular, least conflict), page-level locks (medium), table-level locks (coarsest, most conflict). Shared lock (S-lock): multiple readers allowed, no writes. Exclusive lock (X-lock): one writer, no readers. Intent locks: signal at table/page level what lock is held at row level.

Q50 — Isolation levels recap: READ UNCOMMITTED (dirty reads possible), READ COMMITTED (no dirty reads, default in PostgreSQL), REPEATABLE READ (no non-repeatable reads, default in MySQL InnoDB), SERIALIZABLE (no phantom reads, full isolation, slowest). Higher isolation = fewer anomalies but more lock contention and reduced throughput.

More Intermediate Questions (Q36–Q55)

Q36. Explain the difference between a clustered and a non-clustered index with an example. ▼

A clustered index determines the physical order of rows in the table — data rows ARE the leaf nodes of the B-tree. There can be only one per table (the PRIMARY KEY in InnoDB). Range scans are fast because physically adjacent rows are close on disk. A non-clustered index is a separate B-tree structure that stores indexed values + pointers (row IDs/PKs) back to the actual rows. Multiple allowed per table. Requires two lookups: one to find the pointer, one to fetch the row (unless a covering index eliminates the second step).

Q37. What are window functions and how do they differ from regular aggregates? ▼

Regular aggregates (with GROUP BY) collapse multiple rows into one per group — the original rows are lost. Window functions perform calculations across a "window" of related rows but preserve all rows in the output — each row gets an additional computed column. The OVER() clause defines the window. Window functions cannot be used in WHERE (use a subquery/CTE to filter on window results).

SQL — Window vs GROUP BY
-- GROUP BY: collapses rows — one result per dept
SELECT department, AVG(salary) AS avg_sal
FROM employees
GROUP BY department;

-- Window: keeps all rows, adds avg as a column on each row
SELECT
  name, department, salary,
  AVG(salary) OVER (PARTITION BY department) AS dept_avg,
  salary - AVG(salary) OVER (PARTITION BY department) AS diff_from_avg
FROM employees;
Q38. How does PARTITION BY differ from GROUP BY? ▼

Both divide rows into groups for calculations. GROUP BY reduces multiple rows into one summary row per group — you lose individual row details. PARTITION BY (inside OVER) divides rows into groups for window calculations but keeps every row visible. PARTITION BY is only valid inside window function OVER clauses — it never appears in a standalone position like GROUP BY does.

Q4. What is a recursive CTE? When is it used? ▼

A recursive CTE has an anchor member (base case) and a recursive member (references itself) joined by UNION ALL. Runs iteratively until no new rows. Used for: org chart traversal (employee → manager → CEO), tree/category hierarchies, generating number sequences, graph traversal. Always include a termination condition to prevent infinite loops.

Q5. What are the four SQL isolation levels? ▼
  • READ UNCOMMITTED: Dirty reads allowed. Sees uncommitted data. Fastest but dangerous.
  • READ COMMITTED: Only sees committed data. Prevents dirty reads.
  • REPEATABLE READ: Same query returns same results within a transaction. MySQL InnoDB default.
  • SERIALIZABLE: Full isolation — slowest, safest. No concurrency anomalies.
Q6. What is query optimization? What techniques do you use? ▼
  • EXPLAIN / EXPLAIN ANALYZE: Identify full scans, missing indexes, join order
  • Proper indexing: WHERE, JOIN, ORDER BY columns; composite indexes for multi-column filters
  • Avoid functions on indexed columns: WHERE YEAR(date)=2024 → use range instead
  • SELECT only needed columns: Avoid SELECT * with large blob/text fields
  • Keyset pagination: WHERE id > last_id LIMIT n instead of OFFSET on large tables
  • Covering indexes: Include all query columns in index to avoid table fetch
Q7. What is a deadlock? How do you prevent it? ▼

A deadlock occurs when transaction A holds lock 1 and waits for lock 2, while transaction B holds lock 2 and waits for lock 1 — circular wait, neither can proceed. Prevention: access tables/rows in a consistent order; keep transactions short; avoid user interaction inside transactions; use optimistic locking where possible. Most DBs auto-detect and roll back the "cheapest" transaction.

Q8. Optimistic vs pessimistic locking? ▼

Pessimistic: Lock before read/write (SELECT ... FOR UPDATE). Safe but blocks other transactions. Good for high-conflict scenarios. Optimistic: No locks — read with version number; on update, verify version unchanged. If version changed, retry. Implemented with a version or updated_at column. Best for high-read, low-conflict scenarios.

Q9. What is a covering index? ▼

A covering index includes ALL columns a query needs — so the DB answers the query entirely from the index without touching base table rows, eliminating the second lookup. Example: CREATE INDEX idx ON orders (customer_id, order_date) INCLUDE (total, status) covers a query selecting total/status and filtering on customer_id/order_date. Shows as "Using index" in EXPLAIN Extra column.

Q10. What is the N+1 query problem? ▼

1 query fetches N rows, then N additional queries are run for each row to fetch related data. Example: fetch 100 orders (1 query), then for each order fetch the customer (100 queries) = 101 total queries. Fix: use a JOIN to get both in one query, or batch load. Common in ORM-heavy apps. Always inspect generated SQL when using ORMs.

Q45. What are common table expression (CTE) materialization issues in PostgreSQL? ▼

In PostgreSQL, CTEs prior to version 12 were always materialized — their results were computed and stored in memory regardless of how the outer query used them. This prevented the optimizer from pushing filters down into the CTE, often causing full scans. From PG 12+, CTEs are automatically inlined (not materialized) unless they're recursive or contain side effects (writes). You can force behavior with MATERIALIZED or NOT MATERIALIZED hints. In MySQL and most other DBs, CTEs are treated more like inline views and can be optimized through.

SQL — PostgreSQL CTE Hints
-- Force materialization (compute once, cache result)
WITH expensive_calc AS MATERIALIZED (
  SELECT customer_id, SUM(total) ltv
  FROM orders GROUP BY 1
)
SELECT * FROM expensive_calc WHERE ltv > 5000;

-- Force inline (allow optimizer to push filter into CTE)
WITH filtered AS NOT MATERIALIZED (
  SELECT * FROM orders WHERE status = 'completed'
)
SELECT * FROM filtered WHERE total > 1000;

Q41. What is a star schema vs snowflake schema? With diagrams. ▼

Star schema: A central fact table surrounded by denormalized dimension tables. Each dimension is a single table, even if logically it has sub-attributes. Simple JOINs (fact → dim), fast for analytics. Used in most data marts.

Snowflake schema: Dimensions are normalized into multiple related tables (e.g., dim_product → dim_category → dim_department). Saves storage, enforces referential integrity, but requires more JOINs. Common in enterprise warehouses where storage or update anomalies matter.

Q42. Explain database sharding. How does it differ from partitioning? ▼

Partitioning splits a large table into smaller pieces on a single database server. The application still connects to one database — the partition is transparent. Solves storage and query performance for large tables on one machine.

Sharding distributes data across multiple database servers (shards). Each shard holds a subset of data (e.g., users A-M on shard 1, N-Z on shard 2). Enables horizontal scaling beyond a single server's capacity. Adds complexity: cross-shard queries (e.g., aggregating across all users) require application-level coordination or a query router. Used at very large scale: hundreds of millions of users, petabyte-scale data.

Q43. What are window frame clauses? Explain ROWS vs RANGE. ▼
SQL — Window Frame Examples
-- ROWS: physical rows relative to current row (most common)
SUM(amount) OVER (
  ORDER BY date
  ROWS BETWEEN 2 PRECEDING AND CURRENT ROW  -- 3-row running sum
)

-- RANGE: logical range (peers with same ORDER BY value)
SUM(amount) OVER (
  ORDER BY date
  RANGE BETWEEN INTERVAL 7 DAY PRECEDING AND CURRENT ROW
)  -- all rows within last 7 days (not just 7 rows)

-- Common frame boundaries:
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW  -- cumulative sum
ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING   -- reverse cumulative
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING -- entire partition
ROWS BETWEEN 6 PRECEDING AND CURRENT ROW          -- 7-row window

ROWS counts physical rows. RANGE groups all rows with the same ORDER BY value as peers (useful for date-based windows where multiple rows share the same date). For most running totals and moving averages, ROWS is preferred for its predictable behavior.

Q45. What is an execution plan cache? How does it affect performance? ▼

When a query runs, the optimizer creates an execution plan (which indexes to use, join order, etc.). This planning has a cost. The plan cache (query cache in MySQL, plan cache in SQL Server) stores compiled plans and reuses them for identical queries — avoiding re-planning on every execution. Stored procedures benefit most from this: they are compiled once on first call and cached. Ad-hoc SQL with different literal values every time (e.g., WHERE id = 42 vs WHERE id = 43) may not reuse plans unless parameterized. In MySQL 8.0+, the query cache was removed — use stored procedures and prepared statements for plan reuse.

Q46. Explain SCD (Slowly Changing Dimensions) and when to use Type 2. ▼

SCDs handle how dimension data changes over time in data warehouses. Type 2 is most commonly used because it provides complete point-in-time accuracy: when a customer's city changes, a new row is inserted with the new city, the old row is expired with an end date. Fact table JOINs use both the business key AND the date to match the right dimension row. Use Type 2 whenever you need to answer questions like "where was this customer when they placed this order?" or "what department was this employee in when they made this sale?" — any time the historical context of a transaction matters.

Q47–50. OLAP vs OLTP | CAP theorem | Connection pooling | Database normalization anomalies ▼

Q47 — OLAP vs OLTP: OLTP (Online Transaction Processing) handles frequent, small, fast reads/writes for day-to-day operations — highly normalized, low latency, ACID-compliant. OLAP (Online Analytical Processing) handles complex aggregation queries over large historical datasets for analytics — denormalized (star/snowflake), column-oriented storage, batch-loaded. Examples: MySQL for OLTP, Redshift/BigQuery/Snowflake for OLAP.

Q48 — CAP Theorem: Distributed systems can guarantee at most two of three: Consistency (all nodes see same data), Availability (every request gets a response), Partition Tolerance (system continues during network splits). Traditional RDBMS prioritize CP (Consistency + Partition Tolerance). Cassandra/DynamoDB prioritize AP. You can't have all three when network partitions occur.

Q49 — Connection pooling: Opening a new database connection is expensive (TCP handshake, auth, session setup). A connection pool maintains a set of pre-opened connections and reuses them. Applications borrow a connection from the pool, use it, and return it. Tools: PgBouncer, HikariCP, ProxySQL. Prevents "connection exhaustion" and dramatically reduces latency under high concurrency.

Q50 — Normalization anomalies: Without normalization, three types of anomalies occur: (1) Update anomaly: same data in multiple rows — update one and others become stale. (2) Insert anomaly: can't insert a fact without inserting another unrelated fact (e.g., can't add a department without an employee). (3) Delete anomaly: deleting a row removes important data (e.g., deleting last employee in a department removes the department's name). Normalization eliminates these by ensuring each fact is stored exactly once.

WITH daily_rev AS (
  SELECT
    DATE(created_at) AS dt,
    SUM(total)       AS revenue
  FROM orders
  GROUP BY 1
),
with_prev AS (
  SELECT
    dt,
    revenue,
    LAG(revenue) OVER (ORDER BY dt) AS prev_day
  FROM daily_rev
)

Q43. Implement SCD Type 2 update as a stored procedure. ▼
SQL — SCD Type 2 ETL Procedure
DELIMITER $$
CREATE PROCEDURE UpdateCustomerSCD2(
  IN p_customer_id  INT,
  IN p_name         VARCHAR(100),
  IN p_city         VARCHAR(100),
  IN p_country      VARCHAR(50)
)
BEGIN
  DECLARE v_changed BOOLEAN DEFAULT FALSE;

  -- Check if any tracked attribute changed
  SELECT (city != p_city OR country != p_country)
  INTO v_changed
  FROM dim_customer
  WHERE customer_id = p_customer_id AND is_current = 1;

  IF v_changed THEN
    -- Step 1: expire the old row
    UPDATE dim_customer
    SET   is_current   = 0,
          eff_end_date = DATE_SUB(CURDATE(), INTERVAL 1 DAY)
    WHERE customer_id  = p_customer_id
      AND   is_current    = 1;

    -- Step 2: insert new current row
    INSERT INTO dim_customer
      (customer_id, name, city, country,
       is_current, eff_start_date, eff_end_date)
    VALUES
      (p_customer_id, p_name, p_city, p_country,
       1, CURDATE(), '9999-12-31');

    SELECT 'UPDATED' AS result;
  ELSE
    -- No tracked attribute changed — just update non-SCD fields
    UPDATE dim_customer
    SET   name = p_name
    WHERE customer_id = p_customer_id AND is_current = 1;
    SELECT 'NO CHANGE' AS result;
  END IF;
END$$
DELIMITER ;

Q44. Write a query for a retention heatmap (cohort × months after signup). ▼
SQL — Cohort Retention Heatmap
WITH
cohorts AS (
  SELECT
    customer_id,
    DATE_FORMAT(MIN(order_date), '%Y-%m') AS cohort_month
  FROM orders
  GROUP BY customer_id
),
retention AS (
  SELECT
    c.cohort_month,
    TIMESTAMPDIFF(MONTH,
      STR_TO_DATE(CONCAT(c.cohort_month,'-01'),'%Y-%m-%d'),
      o.order_date
    ) AS months_since_first,
    COUNT(DISTINCT o.customer_id) AS active_users
  FROM cohorts c
  JOIN orders o ON c.customer_id = o.customer_id
  GROUP BY c.cohort_month, 2
)
SELECT
  cohort_month,
  MAX(CASE WHEN months_since_first=0  THEN active_users END) AS m0,
  MAX(CASE WHEN months_since_first=1  THEN active_users END) AS m1,
  MAX(CASE WHEN months_since_first=2  THEN active_users END) AS m2,
  MAX(CASE WHEN months_since_first=3  THEN active_users END) AS m3,
  MAX(CASE WHEN months_since_first=6  THEN active_users END) AS m6
FROM retention
GROUP BY cohort_month
ORDER BY cohort_month;
Q45. Write a dynamic SQL query to calculate revenue for any configurable date range. ▼
SQL — Dynamic Date Range Revenue
DELIMITER $$
CREATE PROCEDURE RevenueByDateRange(
  IN p_start   DATE,
  IN p_end     DATE,
  IN p_group   VARCHAR(10)  -- 'day', 'week', 'month', 'year'
)
BEGIN
  DECLARE v_format VARCHAR(20);
  DECLARE v_sql    TEXT;

  SET v_format = CASE p_group
    WHEN 'day'   THEN '%Y-%m-%d'
    WHEN 'week'  THEN '%Y-W%u'
    WHEN 'month' THEN '%Y-%m'
    WHEN 'year'  THEN '%Y'
    ELSE '%Y-%m'
  END;

  SET v_sql = CONCAT(
    "SELECT DATE_FORMAT(order_date, '", v_format, "') AS period, ",
    "COUNT(*) AS orders, ROUND(SUM(total),2) AS revenue, ROUND(AVG(total),2) AS aov ",
    "FROM orders WHERE order_date BETWEEN ? AND ? ",
    "GROUP BY 1 ORDER BY 1"
  );

  PREPARE stmt FROM v_sql;
  EXECUTE stmt USING p_start, p_end;
  DEALLOCATE PREPARE stmt;
END$$
DELIMITER ;

CALL RevenueByDateRange('2024-01-01', '2024-12-31', 'month');

What is DAX?

DAX (Data Analysis Expressions) is a collection of functions, operators, and constants used in formulas to calculate and return values in Power BI, Power Pivot (Excel), and Azure Analysis Services. It combines the feel of Excel formulas with the power of relational database query concepts.

DAX vs SQL — Key Differences

AspectSQLDAX
PurposeQuery & manipulate databasesDefine calculations in a data model
Execution styleSet-based, writes full queriesExpression-based, defines formulas
Filter awarenessWHERE clause explicitly filtersContext (visual, slicer, row) filters automatically
Runs inRDBMS (MySQL, PostgreSQL, etc.)Power BI, Power Pivot, SSAS Tabular
ResultsReturns rows & columnsReturns a scalar value or table
Time intelligenceManual date calculationsBuilt-in: TOTALYTD, SAMEPERIODLASTYEAR, etc.

Where DAX Lives in Power BI

📏

Measures

Dynamic calculations that respond to filters and slicers. Computed at query time. No new column in table. Example: [Total Sales]

➕

Calculated Columns

New column added to a table in the data model. Computed at data refresh time. Stored in memory. Example: [Full Name] = [First] & " " & [Last]

🗂️

Calculated Tables

Virtual tables created from DAX expressions. Used for date tables, disconnected parameter tables, bridging. Example: CALENDAR(), CROSSJOIN()

Always prefer Measures over Calculated Columns for aggregations. Measures are computed dynamically and don't consume RAM. Calculated Columns are materialized and stored — use them only for row-level attributes like concatenating name fields or categorizing rows.

DAX Syntax Basics

DAX — Syntax Reference
-- Measure (defined in Power BI Measure pane)
Total Sales = SUM(Sales[Amount])

-- Calculated Column (added to a table)
Sales[Profit Margin %] =
  DIVIDE(Sales[Profit], Sales[Revenue], 0)

-- Referencing a table column: TableName[ColumnName]
Products[Price]

-- Referencing a measure: [MeasureName] (no table prefix)
[Total Sales]

-- Variables improve readability and performance
Profit % =
VAR vRevenue = SUM(Sales[Revenue])
VAR vCost    = SUM(Sales[Cost])
RETURN
  DIVIDE(vRevenue - vCost, vRevenue, 0)

-- Comments: -- single line, /* multi line */
Sales Tax = Sales[Amount] * 0.18  -- 18% GST

🎯 Chapter 3 — Foundation

Evaluation Context

Evaluation context is the single most important concept in DAX. Every DAX formula is evaluated inside a context that determines which rows and columns are visible. Miss this and DAX will never make sense. Get it and everything clicks.

Two Types of Context

📋

Row Context

Created when DAX iterates over a table row by row. Each row is the "current row." Calculated columns always have row context. Iterator functions (SUMX, FILTER) create row context. Important: measures do NOT have row context by themselves — they aggregate.

🔍

Filter Context

The set of active filters applied to the data model. Comes from: visual filters, slicers, page filters, report filters, row/column headers in a matrix, and the CALCULATE function. Filter context restricts which rows participate in aggregations.

When a measure is evaluated, it always runs inside the filter context of the visual. When a calculated column or iterator runs, it uses row context. CALCULATE is the bridge — it creates a new filter context, optionally building on the existing one.

Row Context in Action

DAX — Row Context Examples
-- Calculated column: row context exists — each row knows its own values
Sales[Line Total] = Sales[Unit Price] * Sales[Quantity]
-- [Unit Price] and [Quantity] refer to THIS ROW's values

-- SUMX creates row context as it iterates
Revenue (X) =
SUMX(
  Sales,                               -- iterate over Sales table
  Sales[Unit Price] * Sales[Quantity]  -- expression evaluated for EACH row
)
-- Different from SUM(Sales[Amount]) if Amount column doesn't pre-compute the product

-- FILTER creates row context
High Value Sales =
CALCULATE(
  SUM(Sales[Amount]),
  FILTER(Sales, Sales[Amount] > 10000)
  -- FILTER iterates Sales row by row (row context), keeping rows where Amount > 10000
)

Filter Context in Action

DAX — Filter Context Examples
-- A simple SUM measure: affected by whatever filter context exists
Total Sales = SUM(Sales[Amount])

-- In a matrix with Region on rows:
--   Row "North" → filter context filters Sales to Region = North
--   Row "South" → filter context filters Sales to Region = South
--   Grand Total → no region filter, all rows included

-- CALCULATE changes filter context
Electronics Sales =
CALCULATE(
  SUM(Sales[Amount]),
  Products[Category] = "Electronics"
  -- Regardless of what category filter the visual applies,
  -- this measure ALWAYS filters to Electronics
)

-- ALL() removes filter context from a column
% of Total =
DIVIDE(
  [Total Sales],
  CALCULATE([Total Sales], ALL(Sales))
  -- ALL(Sales) removes ALL filters from the Sales table
  -- numerator is filtered (current context), denominator is grand total
)

Context Transition

When CALCULATE is used inside a row context (calculated column or SUMX), it automatically converts the row context into an equivalent filter context. This is called context transition. Every unique combination of column values in the current row becomes a filter. This is powerful but can cause performance issues — be aware when nesting CALCULATE inside iterators.

DAX — Context Transition
-- Context transition example in a calculated column
Customers[Total Purchases] =
CALCULATE(SUM(Sales[Amount]))
-- Row context (CustomerID = 42) transitions to filter context
-- CALCULATE sees: filter Sales where CustomerID = 42
-- Result: total sales for THIS customer only

-- Without CALCULATE, SUM would return the grand total (no row context in measures)
Customers[Wrong Total] = SUM(Sales[Amount])
-- Returns GRAND TOTAL for every row — wrong!

Measures — Theory & Practice

Measures are the heart of Power BI analytics. They are dynamic formulas that evaluate in the filter context of whatever visual they're placed in. A single measure adapts to every visual without rewriting.

Implicit vs Explicit Measures

Implicit measures are created when you drag a numeric field into a visual and Power BI auto-sums it. They are inflexible — you can't reference them from other measures, format them precisely, or apply complex logic. Always create explicit measures with the Measure pane. Professional Power BI models have zero implicit measures.

Essential Measure Patterns

DAX — Core Measure Patterns
-- 1. Basic aggregation measures
Total Revenue    = SUM(Sales[Revenue])
Total Orders     = COUNTROWS(Sales)
Distinct Customers = DISTINCTCOUNT(Sales[CustomerID])
Avg Order Value  = AVERAGE(Sales[Amount])

-- 2. Safe division (returns 0 or BLANK on divide-by-zero)
Profit Margin % =
DIVIDE(
  [Total Revenue] - [Total Cost],
  [Total Revenue],
  0  -- alternate result when denominator = 0
)

-- 3. Conditional measure with CALCULATE + filter
Online Revenue =
CALCULATE(
  [Total Revenue],
  Sales[Channel] = "Online"
)

-- 4. % of Total (grand total stays in denominator)
Revenue % of Total =
DIVIDE(
  [Total Revenue],
  CALCULATE([Total Revenue], ALL(Sales))
)

-- 5. % of parent row (for matrix visuals)
Revenue % of Category =
DIVIDE(
  [Total Revenue],
  CALCULATE([Total Revenue], ALLSELECTED(Products[Category]))
)

-- 6. Rank within context
Product Rank =
RANKX(
  ALL(Products[ProductName]),
  [Total Revenue],
  ,
  DESC
)

-- 7. Cumulative (running) total
Cumulative Revenue =
CALCULATE(
  [Total Revenue],
  FILTER(
    ALL(Date[Date]),
    Date[Date] <= MAX(Date[Date])
  )
)

-- 8. Dynamic title based on slicer selection
Selected Region Title =
IF(
  HASONEVALUE(Regions[Region]),
  SELECTEDVALUE(Regions[Region]) & " — Revenue Summary",
  "All Regions — Revenue Summary"
)

Measure Organization — Display Folders

Create a dedicated empty table called "_Measures" (using DATATABLE with no rows) and store all your measures there. This keeps measures organized, separate from data tables, and easy to find. Use Display Folders within that table to group measures by category (Sales, Finance, HR, Time Intelligence).

FILTER, ALL & ALLEXCEPT

These functions control which rows are included in calculations by adding, removing, or modifying filter context. They are used almost exclusively inside CALCULATE.

FILTER — Row-by-Row Selection

DAX — FILTER Examples
-- FILTER returns a table (subset of rows)
Revenue > 10K Orders =
CALCULATE(
  [Total Revenue],
  FILTER(Sales, Sales[Amount] > 10000)
)

-- Multiple conditions in FILTER
Premium Online Sales =
CALCULATE(
  [Total Revenue],
  FILTER(Sales,
    Sales[Amount] > 5000 &&
    Sales[Channel] = "Online"
  )
)

-- FILTER with RELATED (from related table)
Electronics Revenue =
CALCULATE(
  [Total Revenue],
  FILTER(Sales,
    RELATED(Products[Category]) = "Electronics"
  )
)
-- Note: prefer simple column filter in CALCULATE over FILTER+RELATED for performance

-- Better: direct column filter (uses VertiPaq index, faster)
Electronics Revenue v2 =
CALCULATE([Total Revenue], Products[Category] = "Electronics")

ALL, ALLEXCEPT, ALLSELECTED

DAX — ALL Family
-- ALL(table): removes ALL filters from entire table
Grand Total Revenue =
CALCULATE([Total Revenue], ALL(Sales))

-- ALL(column): removes filter from one column only
Revenue % of All Products =
DIVIDE(
  [Total Revenue],
  CALCULATE([Total Revenue], ALL(Products[ProductName]))
)

-- ALLEXCEPT: remove all filters EXCEPT specified columns
-- Useful: % of total per category, keeping category filter
Revenue % of Category =
DIVIDE(
  [Total Revenue],
  CALCULATE([Total Revenue], ALLEXCEPT(Products, Products[Category]))
)

Revenue % of Filtered Total =
DIVIDE(
  [Total Revenue],
  CALCULATE([Total Revenue], ALLSELECTED(Products[ProductName]))
)

Total Revenue No Date Filter =
CALCULATE([Total Revenue], REMOVEFILTERS(Date))
⚡ Chapter 8 — Key Function

CALCULATE & CALCULATETABLE

CALCULATE is the most powerful and most used function in DAX. It evaluates an expression while modifying the filter context. Mastering CALCULATE is mastering DAX.

CALCULATE Syntax & How It Works

CALCULATE( <expression>, [<filter1>], [<filter2>], ... )

Filters can be: boolean predicates (Sales[Channel] = "Online"), table functions (FILTER, ALL, VALUES), or time intelligence functions (SAMEPERIODLASTYEAR). Filters are AND-ed together. CALCULATE first adds/overrides filters, then evaluates the expression in the new context.

DAX — CALCULATE Deep Examples
-- Single filter override
North Region Sales =
CALCULATE([Total Revenue], Regions[Name] = "North")

-- Multiple filters (AND logic)
North Online 2024 =
CALCULATE(
  [Total Revenue],
  Regions[Name]   = "North",
  Sales[Channel]  = "Online",
  YEAR(Sales[OrderDate]) = 2024
)

-- IN operator for multiple values
Top Category Revenue =
CALCULATE(
  [Total Revenue],
  Products[Category] IN {"Electronics", "Mobiles"}
)

-- Preserve existing filter + add new one (default behavior)
Budget Sales (Excl. Returns) =
CALCULATE(
  [Total Revenue],
  Sales[Type] <> "Return"
  -- The visual's existing filters (date, region, etc.) still apply
  -- We only ADD a new filter: exclude returns
)

-- KEEPFILTERS: add filter without overriding existing
Electronics in Context =
CALCULATE(
  [Total Revenue],
  KEEPFILTERS(Products[Category] = "Electronics")
)

-- CALCULATETABLE: same as CALCULATE but returns a table
Online Sales Table =
CALCULATETABLE(
  Sales,
  Sales[Channel] = "Online"
)
-- Use in COUNTROWS, SUMX, TOPN, etc.

-- Nested CALCULATE — inner overrides outer for same column
Always North =
CALCULATE(
  CALCULATE([Total Revenue], Regions[Name] = "North"),
  Regions[Name] = "South"
)
-- Inner wins: returns North revenue regardless of outer filter
🕐 Time Intelligence — Deep Dive

Time Intelligence

Time intelligence functions automatically navigate your date table to calculate period-over-period comparisons, year-to-date totals, rolling averages, and more. They require a properly marked Date table with a continuous date range.

Date Table Requirements

  • Must have a column of type Date with no gaps — every calendar date must exist
  • Must be marked as a Date Table in Power BI (Table Tools → Mark as Date Table)
  • The date column must be unique — one row per date
  • Your fact table must have a relationship to the Date table's date column

Period-to-Date Functions

DAX — YTD, QTD, MTD
-- Year-to-Date (from Jan 1 to the last visible date)
Revenue YTD =
TOTALYTD([Total Revenue], Date[Date])

-- YTD with custom fiscal year end (e.g., March 31 for Indian FY)
Revenue FY-YTD =
TOTALYTD([Total Revenue], Date[Date], "03-31")

-- Quarter-to-Date

Theory (Q1–Q12)

Q1. What is DAX and what is it used for? ▼

DAX (Data Analysis Expressions) is a formula language used in Power BI, Power Pivot (Excel), and Azure Analysis Services. It's used to define: Measures (dynamic calculations like Total Sales, Profit %), Calculated Columns (new table columns computed row by row), and Calculated Tables (virtual tables like a Date dimension). DAX is expression-based — you define what to calculate, not how to loop through data.

Q2. What is the difference between a Measure and a Calculated Column? ▼

Q3. What is filter context? ▼

Filter context is the set of active filters that determine which rows participate in a DAX calculation. It comes from: report-level filters, page filters, visual-level filters, slicer selections, and row/column headers in a matrix. A measure like SUM(Sales[Amount]) automatically returns different results on each row of a matrix because the row header creates a different filter context for each cell.

Q4. What is row context? ▼

Row context is created when DAX iterates over a table row by row. It exists in: calculated column definitions (each row has its own context), and iterator functions like SUMX, FILTER, ADDCOLUMNS. In row context, Sales[Amount] refers to THIS row's Amount value. Measures don't have row context by default — they need SUMX or CALCULATE to work row by row.

Q5. What does CALCULATE do? ▼

CALCULATE evaluates an expression while modifying the filter context. It is the most important function in DAX. Syntax: CALCULATE(expression, filter1, filter2, ...). The filters add to, override, or remove existing filters before the expression is evaluated. Without CALCULATE, you cannot change the context a measure runs in — it will always use whatever the visual provides.

Q6. What is the difference between SUM and SUMX? ▼

SUM(Table[Column]) sums a single column directly — fast, no row context created. SUMX(Table, expression) iterates over every row of Table, evaluates the expression in each row's context, then sums the results. Use SUMX when you need to calculate something per row first: SUMX(Sales, Sales[Qty] * Sales[Price]) multiplies then sums — you can't do this with a single SUM if there's no pre-computed total column.

Q7. What is ALL() used for? ▼

ALL() removes filter context from a table or column. Used inside CALCULATE to create "ignore filter" measures. CALCULATE([Total Sales], ALL(Products)) returns total sales for all products regardless of which product the visual is filtering on. It's essential for % of total calculations: divide the filtered value by the ALL() version to get the proportion.

Q8. What is BLANK() in DAX? How is it different from NULL? ▼

BLANK() is DAX's equivalent of absence of value — similar to NULL in SQL but with key differences. Arithmetic with BLANK treats it as 0 or empty string (BLANK() + 5 = 5). Comparisons: BLANK() = BLANK() returns TRUE. BLANK() propagates through most functions but not through arithmetic. Use ISBLANK() to test for it. In Power BI visuals, measures returning BLANK() are hidden (cell appears empty), which is useful for hiding zero rows.

Q9. Why do time intelligence functions require a Date table? ▼

Time intelligence functions (TOTALYTD, SAMEPERIODLASTYEAR, PREVIOUSMONTH, etc.) navigate the date dimension to find "same period" dates. They need: (1) a Date table marked as a Date Table in Power BI, (2) a column of DATE type with no gaps (every calendar day present), (3) unique dates (one row per day), and (4) a relationship from the fact table to this Date table. Without these, the functions produce incorrect or blank results.

Q10. What is DIVIDE() and why is it preferred over /? ▼

DIVIDE(numerator, denominator, [alternate]) is a safe division function. If the denominator is 0 or BLANK, it returns the alternate value (default: BLANK()) instead of throwing an error. Using / directly can cause "division by zero" errors visible in visuals. Always use DIVIDE for any division involving measures or user data where the denominator might be 0.

Q11. What is the purpose of VAR in DAX? ▼

VAR stores the result of an expression in a named variable, and RETURN specifies what the measure ultimately returns. Benefits: (1) Performance — the variable is computed once even if referenced multiple times; (2) Readability — complex formulas become readable step-by-step; (3) Debugging — temporarily RETURN a variable to inspect its value; (4) Context safety — a variable captures the value at the point of declaration, preventing confusing context shifts in nested calculations.

Q12. What is SELECTEDVALUE() and HASONEVALUE()? ▼

SELECTEDVALUE(column, default) returns the value of a column when it is filtered to exactly one value (e.g., one item selected in a slicer). Returns the default (or BLANK) when multiple values are selected. HASONEVALUE(column) returns TRUE when exactly one value is visible in the filter context. Use them for dynamic titles, conditional formatting, and single-selection-dependent logic.

DAX Q&A — Intermediate (30 Questions)

CALCULATE, time intelligence, X-functions, context transition, and real-world Power BI patterns.

Theory (Q1–Q12)

Q1. Explain context transition in DAX. ▼

Context transition happens when CALCULATE is used inside a row context (calculated column or iterator). CALCULATE converts each unique combination of column values in the current row into an equivalent filter context. Example: in a calculated column, CALCULATE(SUM(Sales[Amount])) doesn't return the grand total — it applies the current row's CustomerID as a filter and returns that customer's total sales. This is a key advanced concept that enables powerful row-level aggregation in calculated columns.

Q2. What is the difference between ALL() and ALLSELECTED()? ▼

ALL() removes ALL filters — including those from slicers, page filters, and visual filters. The result is always the absolute grand total. ALLSELECTED() removes row/column header filters from the visual but keeps slicer and external filter selections. This makes ALLSELECTED perfect for "% of what's currently filtered" — if a user filters to 2024 via a slicer, ALLSELECTED keeps that year filter while removing product/region filters from the matrix.

Q3. When would you use KEEPFILTERS()? ▼

Normally, CALCULATE overrides an existing filter on the same column with the new one. KEEPFILTERS makes CALCULATE intersect filters instead. Example: if the visual has Category = "Electronics" and you use CALCULATE([Revenue], KEEPFILTERS(Category = "Mobiles")), the result is BLANK (Electronics AND Mobiles is an empty intersection). Without KEEPFILTERS, it would override to Mobiles. Use KEEPFILTERS when you want the new filter to narrow down the existing context rather than replace it.

Q4. What is USERELATIONSHIP() and when do you need it? ▼

USERELATIONSHIP activates an inactive relationship for the duration of a CALCULATE expression. Common scenario: a Sales table has both an OrderDate and a ShipDate, both with a relationship to the Date table — but only one can be active at a time. To build a "Revenue by Ship Date" measure without changing the model's active relationship, you use CALCULATE([Total Revenue], USERELATIONSHIP(Sales[ShipDate], Date[Date])). This temporarily uses the ShipDate→Date relationship for that one calculation.

Q5. What is RANKX() and what are its parameters? ▼

RANKX ranks a value against a table of values. Parameters: RANKX(table, expression, [value], [order], [ties]). table: the set of values to rank against (usually ALL or ALLSELECTED of a dimension). expression: what to rank by (usually a measure). value: the value to rank (blank = use current context). order: DESC (default, 1=highest) or ASC. ties: DENSE (no gaps: 1,2,2,3) or SKIP (1,2,2,4). DENSE is usually preferred for clean rankings.

Q6. Explain the difference between EARLIER() and VAR in row context. ▼

Both solve the "access outer row context" problem but VAR is the modern approach. EARLIER() references the row context one level "up" from a nested row context — it was the only way before variables. Example: comparing each row's salary to the average salary of its category in a calculated column. With EARLIER: AVERAGEX(FILTER(Employees, [Category]=EARLIER([Category])), [Salary]). With VAR (cleaner): VAR vCat = [Category] RETURN AVERAGEX(FILTER(Employees, [Category]=vCat), [Salary]). Always use VAR in modern DAX — EARLIER is legacy.

Q7. What is a semi-additive measure? Give examples. ▼

A semi-additive measure cannot be meaningfully summed across the time dimension, even though it can be summed across other dimensions (like product or region). Examples: Inventory quantity (summing Jan + Feb stock is meaningless — you want the end-of-month balance), Bank account balance, Headcount, Active subscribers. For these, use LASTDATE(), LASTNONBLANK(), or AVERAGEX over time rather than SUM across dates.

Q8. What is the VertiPaq engine and why does it matter for DAX? ▼

VertiPaq is Power BI's in-memory columnar storage engine. It compresses data by column using dictionary encoding and RLE (Run-Length Encoding) — this is why a column with many repeated values (like "Country") is tiny in memory. DAX formulas execute against this engine via Storage Engine queries (fast, parallelized) and Formula Engine computations (single-threaded, slower). Good DAX pushes as much work as possible to the Storage Engine (column filters, aggregations) and minimizes Formula Engine work (which happens when using FILTER with measures, context transition, etc.).

Q9. What is ALLEXCEPT() and how does it differ from ALL()? ▼

ALL(Table) removes all filters from the entire table. ALLEXCEPT(Table, col1, col2) removes all filters from the table except the specified columns. This is useful for "% of subtotal" in a matrix: if you have Region and Category on rows, and you want % of region total (keeping Region filter but removing Category), use ALLEXCEPT(Products, Products[Region]) in the denominator's CALCULATE.

Q10. What are the main time intelligence functions in DAX? ▼
  • TOTALYTD / TOTALQTD / TOTALMTD: Accumulate from start of period to current date
  • SAMEPERIODLASTYEAR: Same date range, one year back
  • PREVIOUSYEAR / PREVIOUSQUARTER / PREVIOUSMONTH: Full prior period
  • DATEADD: Shift dates by N intervals (days, months, quarters, years)
  • DATESINPERIOD: All dates in a rolling window (e.g., last 90 days)
  • DATESMTD / DATESQTD / DATESYTD: Return table of dates from start of period
  • FIRSTDATE / LASTDATE: First or last date in current context
  • LASTNONBLANK: Last date with data — essential for semi-additive measures
Q11. What is the difference between RELATED() and RELATEDTABLE()? ▼

RELATED() follows a many-to-one relationship and returns a single value from the "one" side. Used in calculated columns on the "many" side. Example: Sales[Category] = RELATED(Products[Category]) — each Sales row gets its product's category. RELATEDTABLE() follows a one-to-many relationship and returns a table of all related rows from the "many" side. Used in calculated columns on the "one" side. Example: Customers[OrderCount] = COUNTROWS(RELATEDTABLE(Sales)).

Q12. What is Row-Level Security (RLS) in Power BI? ▼

RLS restricts which rows of data each user can see in a published report. You define Roles in Power BI Desktop, and each role has a DAX filter expression applied to one or more tables (e.g., [Region] = "North"). When a user views the report, Power BI applies the filter of their assigned role — they only see North data. Dynamic RLS uses USERPRINCIPALNAME() to filter based on the logged-in user's identity, matching against a security mapping table.

Theory (Q1–Q15)

Q1. Explain the Storage Engine vs Formula Engine in Power BI. ▼

DAX execution uses two engines. The Storage Engine (SE) is multi-threaded, reads VertiPaq compressed columns, performs aggregations and simple filters extremely fast using columnar indexes. The Formula Engine (FE) is single-threaded, handles complex logic, iterators, context transitions, and non-SARGable operations. Good DAX pushes work to the SE (column equality filters, simple aggregations) and minimizes FE work (FILTER with measures, nested iterators). Tools like DAX Studio show SE and FE query logs, helping you identify which operations are bottlenecks.

Q2. What is cardinality in Power BI and how does it affect performance? ▼

Cardinality = number of unique values in a column. High-cardinality columns (UUIDs, timestamps, free text) compress poorly in VertiPaq, consume more RAM, and slow down filter operations. Reduce cardinality by: rounding timestamps to date (remove time component), using integer keys instead of string keys for relationships, removing high-cardinality columns that aren't needed in visuals, using a date table instead of datetime in the fact table. Low cardinality columns (country, status, boolean) compress extremely well and are fast to filter.

Q3. What is bidirectional cross-filtering and when is it dangerous? ▼

In a standard relationship, filters flow from the one-side to the many-side. With bidirectional cross-filtering, filters also flow from many to one. This enables some convenient patterns (counting products that have been sold, filtering dimension by fact data) but is dangerous in complex models: it can cause circular filter propagation, ambiguous filter paths, and significant performance degradation. Best practice: use single-direction relationships by default, and use CROSSFILTER() inside CALCULATE when you need bidirectional behavior for a specific measure.

Q4. What is the difference between GENERATE() and ADDCOLUMNS()? ▼

ADDCOLUMNS(table, colName, expr, ...) adds calculated columns to an existing table — it returns the original table with new columns appended. GENERATE(table1, table2expr) creates a row-by-row cross-join: for each row in table1, evaluates table2expr in that row's context and appends the results. ADDCOLUMNS is used when you just want to enrich a table with computed columns. GENERATE is used when you need to expand a table by attaching related row sets to each row — like a lateral join in SQL.

Q6 — DAX Studio: Free tool for measuring and optimizing DAX. Q7 — Disconnected tables: Tables with no relationship to the data model, used as parameter sources. Example: a "Sales Target" table where each row is a target option (₹1M, ₹5M, ₹10M). Q11–15. Composite models | Aggregations | DirectQuery limitations | CALCULATE without filters | Tabular model roles ▼

Q11 — Composite models: Power BI composite models mix Import mode (VertiPaq in-memory) and DirectQuery mode tables in the same model. Small dimension tables import for speed; huge fact tables query live from the database. The Import dimensions filter DirectQuery facts via the relationship. Enables interactive performance with up-to-date large data.

Q12 — User-Defined Aggregations: For composite models with huge DirectQuery tables, you can define pre-aggregated summary tables in Import mode. Dramatically speeds up high-level reports while still allowing drill-through to transaction data.

Q13 — DirectQuery DAX limitations: DAX functions that materialize large intermediate tables (complex FILTER, ADDCOLUMNS, GENERATE) can be extremely slow in DirectQuery as they translate to SQL subqueries. Q14 — CALCULATE() with no filters: CALCULATE(expression) with no filter arguments still triggers context transition — it converts any active row context into filter context. Q42. What is query plan caching? How does it affect stored procedures? ▼

When a query is first executed, the optimizer parses it, creates an execution plan, and caches it. Subsequent calls with the same parameterized shape reuse the cached plan without re-optimization. Stored procedures benefit the most — their queries are compiled and cached when first called, making repeated calls very fast. However, plan caching can cause problems: if statistics change dramatically (e.g., a table grows from 1,000 to 100M rows), the cached plan might no longer be optimal. Solutions: CALL sp_recompile('procedure_name') to force re-compilation, or restructure queries to avoid parameter sniffing.

Q43. Explain the difference between UNION, INTERSECT, and EXCEPT. ▼

These are set operators that combine results of two queries with matching column structures:

SQL
-- UNION: rows in A OR B (deduplicates)
SELECT email FROM customers
UNION
SELECT email FROM suppliers;

-- INTERSECT: rows in BOTH A AND B (PostgreSQL/SQL Server)
SELECT email FROM customers
INTERSECT
SELECT email FROM suppliers;

-- EXCEPT: rows in A but NOT in B (PostgreSQL/SQL Server)
SELECT email FROM customers
EXCEPT
SELECT email FROM suppliers;

-- MySQL workarounds (no INTERSECT/EXCEPT)
-- INTERSECT via JOIN
SELECT a.email FROM customers a
INNER JOIN suppliers b USING(email);
-- EXCEPT via LEFT JOIN anti-join
SELECT a.email FROM customers a
LEFT JOIN suppliers b USING(email)
WHERE b.email IS NULL;

Q45. Write a stored function that computes compound interest. ▼

DELIMITER $$
CREATE FUNCTION CompoundInterest(
  principal  DECIMAL(15,2),
  rate_pct   DECIMAL(6,4),   -- annual rate e.g. 5.25 for 5.25%
  years      INT,
  n_per_year INT              -- compounding freq (12=monthly)
)
RETURNS DECIMAL(15,2)
DETERMINISTIC NO SQL
BEGIN
  -- A = P(1 + r/n)^(n*t)
  RETURN ROUND(
    principal * POW(
      (1 + (rate_pct/100) / n_per_year),
      n_per_year * years
    ), 2
  );
END$$
DELIMITER ;

  balance AS principal,
  CompoundInterest(balance, 5.25, 10, 12) AS value_after_10_years
FROM savings_accounts;

Q47. What is write-ahead logging (WAL) and how does it relate to durability? ▼

Write-Ahead Logging (WAL) is the mechanism that makes the D in ACID possible. Before any data change is written to the actual data file, it is first written to a sequential log file (the redo log / WAL). The log write is very fast (sequential I/O). If the system crashes, the database can recover by replaying the WAL log from the last checkpoint. In MySQL InnoDB, this is the redo log. Because the log is always written first, no committed transaction can ever be lost — even if the main data pages are in the buffer pool and not yet flushed to disk. The tradeoff is that all writes require at least a WAL write, adding some overhead.

Q48. Write a query to calculate a user retention cohort table. ▼
SQL — Cohort Retention
WITH
cohorts AS (
  SELECT
    user_id,
    DATE_FORMAT(MIN(login_date),'%Y-%m') AS cohort_month
  FROM user_sessions
  GROUP BY user_id
),
activity AS (
  SELECT
    s.user_id,
    c.cohort_month,
    TIMESTAMPDIFF(MONTH,
      STR_TO_DATE(CONCAT(c.cohort_month,'-01'),'%Y-%m-%d'),
      STR_TO_DATE(CONCAT(DATE_FORMAT(s.login_date,'%Y-%m'),'-01'),'%Y-%m-%d')
    ) AS month_num
  FROM user_sessions s
  JOIN cohorts       c USING(user_id)
)
SELECT
  cohort_month,
  COUNT(DISTINCT CASE WHEN month_num=0  THEN user_id END) AS m0,
  COUNT(DISTINCT CASE WHEN month_num=1  THEN user_id END) AS m1,
  COUNT(DISTINCT CASE WHEN month_num=2  THEN user_id END) AS m2,
  COUNT(DISTINCT CASE WHEN month_num=3  THEN user_id END) AS m3

Q49. Explain table partitioning — types and a real MySQL example. ▼

Partitioning splits a logically single table into multiple physical storage segments (partitions), invisible to queries. The optimizer prunes partitions — queries only scan relevant ones, skipping others entirely (partition pruning). Types:

  • RANGE: Rows assigned based on a range of values (commonly dates). Best for time-series data.
  • LIST: Rows assigned based on explicit value lists (country = 'India', country = 'USA').
  • HASH: Rows evenly distributed across N partitions by hash of a column. Spreads load evenly.
  • KEY: Similar to HASH but uses MySQL's own hash function on any column type.
SQL — RANGE Partitioning on order_date
CREATE TABLE orders_partitioned (
  id          INT           NOT NULL,
  customer_id INT           NOT NULL,
  order_date  DATE          NOT NULL,
  total       DECIMAL(10,2),
  PRIMARY KEY (id, order_date)  -- partition col must be in PK
)
PARTITION BY RANGE (YEAR(order_date)) (
  PARTITION p2022 VALUES LESS THAN (2023),
  PARTITION p2023 VALUES LESS THAN (2024),
  PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p_future VALUES LESS THAN MAXVALUE
);

-- This query only scans p2024 partition (partition pruning)
SELECT * FROM orders_partitioned
WHERE order_date BETWEEN '2024-01-01' AND '2024-12-31';

-- Drop old partition (instant! vs DELETE which is slow)
ALTER TABLE orders_partitioned DROP PARTITION p2022;
Q50. Write a query to identify data anomalies — values that are statistical outliers. ▼
SQL — Outlier Detection using Z-Score
WITH stats AS (
  SELECT
    AVG(order_value)    AS mean_val,
    STDDEV(order_value) AS std_val
  FROM orders
),
z_scores AS (
  SELECT
    o.id,
    o.customer_id,
    o.order_value,
    s.mean_val,
    s.std_val,
    ABS((o.order_value - s.mean_val) / NULLIF(s.std_val,0)) AS z_score
  FROM  orders o
  CROSS JOIN stats s
)
SELECT id, customer_id, order_value, ROUND(z_score,2) AS z_score
FROM  z_scores
WHERE z_score > 3   -- >3 standard deviations = statistical outlier
ORDER BY z_score DESC;
Q51. What is a covering index and how do you verify it is being used? ▼

A covering index includes all columns needed by a query — the DB answers it entirely from the index without touching actual table rows, eliminating one disk I/O per row. To verify it is used: run EXPLAIN and look for "Using index" in the Extra column (not "Using index condition" or "Using where"). "Using index condition" still means the DB must fetch some rows from the table. Only "Using index" means a true covering index is in play.

SQL
-- Query needs: customer_id (WHERE), order_date (WHERE), total (SELECT)
CREATE INDEX idx_covering
  ON orders(customer_id, order_date, total);

EXPLAIN SELECT order_date, total
FROM  orders
WHERE customer_id = 42
  AND order_date >= '2024-01-01';
-- Extra: 'Using index' ← confirmed covering index

DELIMITER $$
CREATE PROCEDURE LoadCustomerDimSCD2(
  IN p_source_id   INT,
  IN p_name        VARCHAR(100),
  IN p_city        VARCHAR(50),
  IN p_email       VARCHAR(150),
  IN p_effective_dt DATE
)
BEGIN
  DECLARE v_existing_sk  INT           DEFAULT NULL;
  DECLARE v_curr_city    VARCHAR(50);
  DECLARE v_curr_email   VARCHAR(150);

  -- Find current active record
  SELECT  customer_sk, city, email
  INTO    v_existing_sk, v_curr_city, v_curr_email
  FROM    dim_customer
  WHERE   source_customer_id = p_source_id
    AND   is_current        = 1
  LIMIT 1;

  IF v_existing_sk IS NULL THEN
    -- New customer — insert first record
    INSERT INTO dim_customer
      (source_customer_id, name, city, email,
       effective_date, expiry_date, is_current)
    VALUES
      (p_source_id, p_name, p_city, p_email,
       p_effective_dt, '9999-12-31', 1);

  ELSEIF v_curr_city <> p_city OR v_curr_email <> p_email THEN
    -- Attribute changed — close old record
    UPDATE dim_customer
    SET    expiry_date = DATE_SUB(p_effective_dt, INTERVAL 1 DAY),
           is_current  = 0
    WHERE  customer_sk = v_existing_sk;

    -- Insert new version
    INSERT INTO dim_customer
      (source_customer_id, name, city, email,
       effective_date, expiry_date, is_current)
    VALUES
      (p_source_id, p_name, p_city, p_email,
       p_effective_dt, '9999-12-31', 1);
  -- ELSE: no change → do nothing (Type 1 would UPDATE here)
  END IF;
END$$

Q53. What are phantom reads? Which isolation level prevents them? ▼

A phantom read occurs when a transaction reads a set of rows twice, and rows that match the WHERE clause appear or disappear between reads — because another transaction inserted or deleted them in between. Example: Transaction A counts rows WHERE status='active' (gets 100). Transaction B inserts 5 new active rows and commits. Transaction A counts again — gets 105. The new 5 rows are "phantoms." SERIALIZABLE isolation level prevents phantom reads by using range locks that block inserts into the queried range until the transaction completes. REPEATABLE READ prevents non-repeatable reads but not phantoms (though InnoDB's MVCC mitigates this in practice).

Q54. Write a query to implement a session activity timeline (session stitching). ▼
SQL — Session Stitching with LAG
-- Group page views into sessions (new session = 30+ min gap)
WITH gaps AS (
  SELECT
    user_id,
    page_url,
    viewed_at,
    LAG(viewed_at) OVER (
      PARTITION BY user_id
      ORDER BY     viewed_at
    ) AS prev_view
  FROM page_views
),
session_flags AS (
  SELECT
    user_id, page_url, viewed_at,
    CASE
      WHEN prev_view IS NULL
        OR TIMESTAMPDIFF(MINUTE, prev_view, viewed_at) > 30
      THEN 1 ELSE 0
    END AS new_session
  FROM gaps
)
SELECT
  user_id, page_url, viewed_at,
  SUM(new_session) OVER (
    PARTITION BY user_id
    ORDER BY     viewed_at
  ) AS session_id
FROM  session_flags
ORDER BY user_id, viewed_at;
Q55. What is the difference between a natural key, surrogate key, and business key? ▼

A natural key is a unique identifier that exists in the real world — SSN, email, ISBN. Pros: meaningful, no extra column needed. Cons: can change (people change emails), may not be truly unique across systems. A surrogate key is a system-generated meaningless identifier (AUTO_INCREMENT id, UUID). Pros: stable, never changes, joins are fast on integers. Cons: meaningless — you can't derive any information from it. A business key (also called alternate key) is the natural key stored alongside the surrogate key — used by ETL and applications to identify records without relying on internal IDs. Best practice in data warehouses: surrogate key as PK, business key stored as a unique indexed column for lookups.

Q57. How would you identify and fix a slow query in production? Step-by-step process. ▼
  1. Identify: Enable slow query log (slow_query_log=ON, long_query_time=1). Use pt-query-digest or MySQL Workbench to find the top offenders.
  2. Understand: Run EXPLAIN on the slow query. Look for type=ALL (full scans), high rows estimates, Using filesort, Using temporary.
  3. Check indexes: Are the WHERE and JOIN columns indexed? Run SHOW INDEX FROM table_name.
  4. Rewrite if needed: Replace subqueries with JOINs or CTEs. Avoid functions on indexed columns. Eliminate SELECT *. Rewrite NOT IN as NOT EXISTS.
  5. Add indexes: Create indexes on high-cardinality filtered/joined columns. Consider composite/covering indexes.
  6. Update statistics: Run ANALYZE TABLE table_name to refresh optimizer statistics.
  7. Test and measure: Re-run EXPLAIN to confirm plan changed. Benchmark actual execution time. Monitor impact on write performance.
  8. Deploy carefully: On large tables, new indexes should be created during low-traffic windows. Use pt-online-schema-change or gh-ost for zero-downtime index additions.

WITH
daily_orders AS (
  SELECT DISTINCT
    customer_id,
    DATE(order_date) AS ord_day
  FROM orders
),
ranked AS (
  SELECT
    customer_id, ord_day,
    ROW_NUMBER() OVER (
      PARTITION BY customer_id
      ORDER BY     ord_day
    ) AS rn
  FROM daily_orders
),
groups AS (
  SELECT
    customer_id, ord_day,
    DATE_SUB(ord_day, INTERVAL rn DAY) AS grp
  FROM ranked
)
SELECT
  g.customer_id,
  c.name,
  MIN(ord_day) AS streak_start,
  MAX(ord_day) AS streak_end,
  COUNT(*) AS   streak_days
FROM  groups     g
JOIN  customers  c ON c.id = g.customer_id
GROUP BY g.customer_id, c.name, grp
ORDER BY streak_days DESC
LIMIT 10;
